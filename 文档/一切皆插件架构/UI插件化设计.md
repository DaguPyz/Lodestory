# UI 插件化设计

所属主文档：[一切皆插件架构](/Users/yinzhenpu/projects/Lodestory/文档/一切皆插件架构.md)。

本文保留 UI 插件化的原始设计推导，正文中的入口示例和落地表描述设计时的起点，新增扩展接口仍是草案。

当前已实现合并后的 `ui` 插件：其他插件通过 `uiKey` 登记页面和 Provider，`pluginsReady` 后装配单个 React 根，页面通过 `openPage`、`back` 切换并保留已访问页面的组件实例。欢迎页、编辑页和设置页由各自插件登记；应用级导航由 `navigation-layout` 插件提供，工作台内部布局由 `default-layout` 插件提供。窗口外壳 `PageShell` 已由 `window-shell` 插件通过 `@lodestory/sdk/window-shell` 提供，`.app-shell` 和 `.window-titlebar` 专属样式归该插件；公共样式仍留在 `src/styles.css`，由导航布局和工作台显式导入。实际接口和停用边界见 [UI 插件说明](/Users/yinzhenpu/projects/Lodestory/src/plugins/ui/README.md)；本文提出的通用扩展项批次提交、在线增删和撤回失败保留依赖尚未实现。

## 1. 从当前入口找到缺少的能力

目前，[createAppRuntime.ts](/Users/yinzhenpu/projects/Lodestory/src/app/createAppRuntime.ts) 已经只接收插件列表，不依赖主题业务。[themePlugin.ts](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/themePlugin.ts) 在激活时初始化主题，并通过 `themeKey` 提供 `ThemeService`。

但 [main.tsx](/Users/yinzhenpu/projects/Lodestory/src/main.tsx) 仍直接导入 `ThemeProvider`、`ContextMenuProvider` 和 `App`，亲自决定它们的嵌套关系：

```tsx
// 当前入口的简化示意。
const runtime = await createAppRuntime([createThemePlugin()]);
const theme = runtime.get(themeKey);

root.render(
  <ContextMenuProvider>
    <ThemeProvider service={theme}>
      <App />
    </ThemeProvider>
  </ContextMenuProvider>,
);
```

因此，主题的初始化已经由插件负责，但“主题组件进入应用的什么位置、使用哪个服务、什么时候离开”仍由入口负责。增加另一项需要根组件的功能，还得修改入口。

如果目标是入口只选择插件、插件自行接入应用，那么缺少的就是：**插件声明自己提供的 UI，应用按共同约定装配它们，并把这些声明纳入插件生命周期。**

一个通用 `RuntimeProvider` 可以把运行实例传给组件，却不能回答哪些组件需要进入页面、怎样嵌套、如何撤回。因此，传递能力和装配 UI 必须分别有明确的规则。

## 2. 先约定 UI 可以进入哪里

插件不能只交出一个组件，要求应用猜测它应该出现在哪里。`ThemeProvider` 要包住应用，设置项要进入设置页面，编辑器要接收当前文档；这三种接入方式不同。

所以，接收 UI 的一方先公开一个带类型的标识及约定。本文称它为 **UI 插入位置**：它说明这里接收什么组件、传入什么参数、允许几个实现，以及组件实例属于哪个范围。

| 位置 | 谁定义契约并提供实现 | 接收内容 | 数量与范围 |
| --- | --- | --- | --- |
| 根包装位置 | 通用 UI 插件 | 接收 `children` 的 Provider 或包装组件 | 多个，属于窗口 |
| 应用主体位置 | 通用 UI 插件 | 应用外壳组件 | 一个，属于窗口；缺失时不能启动 |
| 设置页面、侧栏等位置 | 拥有相应布局的插件 | 对应区域的组件及约定参数 | 按位置约定单个或多个，属于窗口或项目 |
| 文档编辑位置 | 拥有文档区域的插件 | 接收文档信息的编辑组件 | 按文档创建实例 |

通用 UI 插件只定义装配应用所必需的根位置。设置页面、侧栏、文档参数属于具体业务，应由对应布局插件公开，不能写入内核。

契约由提供者和贡献组件的插件导入同一份定义。提供者在激活时把该位置作为能力交给能力注册表；贡献者把这个位置的能力 key 写进 `requires`，取得它后声明组件。因此，布局先准备好，组件插件才能接入；组件插件未退出时，也不能先卸载它依赖的布局插件。

这里登记的是 **组件定义**。UI 插件渲染时才由 React 创建组件实例，不能在 `activate` 中把含 Hook 的组件当普通函数调用。一个编辑器插件可以贡献一种编辑组件，再由宿主为不同文档分别创建实例；插件实例数量不必等于组件实例数量。

组件实例使用稳定 ID，例如贡献项 ID 与文档 ID 的组合；普通重绘不能换 ID 后意外重建编辑器。组件内部的按钮、输入框仍可保持普通组件，只有需要独立接入和管理的边界才开放为插件位置。

## 3. 有了位置，再明确谁登记、谁渲染

现有能力注册表的一个 key 对应一个能力实现。一个设置区域却可能接收多个插件的组件，不能把每个组件都当成同一个能力 key 的新提供者。

因此，由 **UI 插件创建 UI 登记表**，保存“位置、贡献项 ID、组件定义、排列约束及所属插件”。它通过能力注册表提供登记和挂载能力；登记表本身属于 UI 插件，内核不保存 React 组件。

主题插件取得根包装位置后，将 `ThemeProvider` 与它自己创建的 `ThemeService` 绑定，再提交这一项 UI 声明。示意如下：

```tsx
// 目标设计示意；define / contribute 尚未实现。
requires: [rootWrappersKey],
provides: [themeKey],

async activate(context) {
  const service = await initializeTheme();
  context.provide(themeKey, service);

  const wrappers = context.get(rootWrappersKey);
  context.contribute(wrappers.define({
    id: "theme/provider",
    Component: function ThemeRoot({ children }) {
      return <ThemeProvider service={service}>{children}</ThemeProvider>;
    },
  }));
}
```

`define` 根据位置契约形成尚未公开的贡献项；`context.contribute` 将它暂存并记录当前插件归属。为什么需要暂存、由谁提交，在下一节说明。

这样，创建主题服务、提供主题能力、让主题组件使用同一个服务，都发生在主题插件内。右键菜单插件按同样方式贡献自己的 Provider；应用外壳插件贡献主体组件。入口只配置插件列表，不再逐个导入和排列它们的组件。

UI 插件中的 **UI Host** 是执行这些声明的部分：它取得已提交的登记快照，按位置与顺序创建 React 元素，再交给 React 根渲染。区域宿主在渲染设置页面或文档区域时，也读取对应位置的快照，并按契约传入参数。

页面需要主题时，可以继续通过主题插件公开的 Hook 或 `ThemeService` 契约读取能力。组件插件若使用其他插件的能力，仍要在 `requires` 中声明；能通过 Context 读到对象，不代表可以省略生命周期依赖。

## 4. 登记进入生命周期，才能处理失败和卸载

如果插件在 `activate` 中直接修改 UI 登记表，随后初始化失败，页面可能已经出现这个插件的组件。现有 Core 只撤销能力和事件订阅，并不知道如何撤回这项 UI 登记。

因此，需要把 **有归属、需要暂存和撤回的扩展项** 纳入内核的通用管理范围。UI 贡献项是这类资源的一个具体实现，内核只处理它的生命周期句柄，不导入 React 类型，也不理解主题、设置或编辑器。

`PluginContext` 由 Core 为每个插件创建；插件通过拟新增的 `contribute` 提交扩展项，输入是登记能力生成的未公开句柄。Core 自动关联当前插件 ID，不让插件自行填写归属。句柄怎样校验、公开和撤回，由提供登记能力的插件实现。

| 阶段 | 谁触发 | UI 实现做什么 | 内核保留什么 |
| --- | --- | --- | --- |
| 暂存 | 插件在激活中提交 | 保存未公开声明，尚不进入渲染快照 | 插件与句柄的归属关系 |
| 校验与提交 | Core 在整批激活成功后触发 | 检查位置、冲突和排列关系，成功后一次发布完整快照 | 已提交扩展项及撤回入口 |
| 撤回 | Core 在停用前触发 | 移除对应 UI，并等待宿主确认组件清理 | 确认前保留插件、服务和依赖 |
| 最终释放 | Core 在停用清理中触发 | 释放登记项持有的剩余资源 | 清除归属记录 |

这里有两个不同的公开时点：能力仍需在单个插件激活成功后供后续插件初始化使用；**本批 UI 在所有插件激活并完成 UI 校验之后才一起公开。** 不应把现有能力的逐插件提交改成全部延迟，否则同批消费者无法取得依赖。

提交前，UI 插件先计算完整的新快照，任何校验失败都保持旧快照。批次回滚丢弃未公开的扩展项，再按依赖逆序清理新插件。开始前已有的插件和 UI 保留，失败批次的组件从未呈现给用户。

通用机制管理的是声明和生命周期，不会自动撤销插件已经执行的任意外部操作。文件写入、网络调用等副作用仍由业务自己的规则处理。

## 5. 激活顺序确定后，还要确定组件嵌套顺序

`requires` 能保证“先准备能力，再激活使用者”，却不能保证 React 树中某个 Provider 是另一个组件的祖先。即使主题先激活，把 `ThemeProvider` 放在菜单组件内部，菜单组件仍读不到主题 Context。

因此，UI 契约还需要独立说明 **所需的外层包装** 和 **同位置的排列关系**。例如菜单 Provider 的渲染需要主题 Context，就声明 `theme/provider` 必须在其外层；不能把插件列表顺序当成嵌套约定。

UI 插件在发布快照前处理这些声明：先确认所需包装存在，再根据外层约束排列根包装组件；多贡献位置按显式 `before/after` 关系排列，没有约束的项使用稳定的登记顺序。根包装列表约定从外到内，避免“排在前面”含义不清。

未知位置、重复贡献项 ID、单贡献位置出现多个实现、必需位置为空、缺少所需包装或排列成环，都在提交前报错。错误需要指出位置、贡献项和所属插件，而不是等到组件渲染时报一个模糊的 Context 错误。

包装约束决定 React 结构，能力依赖保护插件生命周期。若某组件必须依赖主题，它既要声明实际使用的主题能力依赖，也要满足所需祖先包装；前者不能代替后者。

## 6. 把规则放回一次启动与停止

### 启动

1. 入口选择插件集合，调用 `createAppRuntime`。运行实例创建业务无关的 Core。
2. Core 根据能力依赖先激活通用 UI 插件。UI 插件创建登记表，提供根位置和通用挂载能力。
3. Core 继续激活主题、菜单、布局等插件。插件提供业务能力，并通过自己的 context 暂存 UI 贡献项；布局插件同时提供它拥有的区域位置。
4. 全部插件激活成功后，Core 请求 UI 实现校验本批贡献项。通过后一次提交登记快照；失败则回滚本批插件和暂存项。
5. 入口取得通用 UI 挂载能力并传入 DOM 容器。UI Host 创建 React 根，根据快照组合根包装和应用主体；区域宿主按自己的位置呈现组件。
6. React 挂载组件。主题组件从主题插件绑定的同一个服务读取状态，区域组件接收宿主传入的窗口、项目或文档参数。

入口最终只需要知道插件集合和通用挂载契约：

```ts
// 目标入口示意；uiHostKey 尚未定义。
const runtime = await createAppRuntime(pluginSet);
await runtime.get(uiHostKey).mount(container);
```

`mount` 的契约应说明：等待首轮挂载确认，挂载失败拒绝 Promise；后续不可恢复的渲染错误交给统一的停止流程。React 的 `root.render` 返回，并不等于整棵组件树已经完成挂载。

### 停止

UI 卸载会执行组件的订阅取消和清理回调，这些回调可能仍需要插件服务。因此，不能先停止服务，再让 React 清理组件。

目标停止顺序是：

```text
允许本次停止，锁定生命周期操作
  → Core 请求撤回本次停止范围内的 UI 扩展项
  → UI Host 提交移除后的树，或卸载整个 React 根
  → 等待组件卸载确认及明确登记的异步清理
  → Core 按依赖逆序调用插件 deactivate
  → 撤销能力、事件订阅、context 和扩展项记录
  → 返回停止结果
```

单个非根区域贡献项停用时，宿主从快照中移除对应组件，并确认其清理完成。整窗停止时，UI Host 一次卸载整个 React 根，不逐个移除外层 Provider；确认前仍保留组件清理所需的服务。

持有根 Provider 的插件只能随整窗停止或重建。若单插件卸载会改变运行中固定的根包装集合或顺序，Core 和 UI Host 必须在任何 UI 撤回或 `deactivate` 之前拒绝，原因见下一节。

React 不会等待普通 Effect 清理函数中的异步工作。需要等待的任务必须通过明确的生命周期入口登记，由 UI 宿主和 Core 协调等待，不能仅凭组件已经从 DOM 消失就认定完成。

| 失败位置 | 后续处理 |
| --- | --- |
| 插件激活或提交前校验失败 | 不公开本批 UI；丢弃暂存项，逆序回滚新插件 |
| 首轮渲染失败 | 撤回已进入 React 的 UI，再停止插件；保留启动错误与清理错误 |
| UI 撤回或卸载确认失败 | 对受影响插件跳过 `deactivate` 和能力撤销，保留插件、服务及依赖，报告停止失败 |
| UI 撤回成功，但 `deactivate` 失败 | 继续撤销该插件的内核登记并记录清理错误；这一点沿用当前停用规则 |

发生撤回失败时，可以继续清理独立插件；仍被保留插件依赖的提供者必须留下。若整个 React 根未能确认卸载，则所有可能仍被这棵树使用的相关插件都不能提前释放。错误应保留阶段、插件 ID 和原始异常，不能用最终的一项清理错误覆盖前面的失败。

**这一规则改变当前 Core 的行为。** 现有代码在 `deactivate` 后，无论是否失败都会撤销登记；它还没有“先撤回 UI、失败则保留依赖”的阶段。当前入口在 React 卸载报错后仍尝试停止运行实例，也需要随新停止协议一起调整。

## 7. 根结构变化为什么需要受控重建

区域组件可以按契约增减，但外层 Provider 被添加、移除或重新排序，可能让整棵编辑器子树重新挂载，丢失组件内尚未保存的状态。

因此，首轮挂载成功后，**一个窗口运行期间固定根包装的集合和顺序**。主题模式变化只更新同一个主题服务，不改根包装结构。要求改变根结构时，单独的在线挂载或卸载应在修改任何记录前被拒绝，转入完整的重建流程。

有未保存正文或项目文件字节时，先由工作台协调 documents 的文档操作与 project-storage 的共享缓冲保存；保存成功或用户已明确同意保留状态后，再卸载 UI、停止旧运行实例并重新装配。保存失败或取消关闭时，保留原窗口与插件，不能先清理再决定是否继续。

开发期 HMR 也要遵守同一顺序：使旧启动流程失效，等待它完成或退出，确认旧 UI 和插件已清理，再启动新实例。不能让两个实例同时操作同一个窗口资源。新的停止实现还应区分正在停止、成功停止和失败保留：并发请求共享进行中的清理，成功后重复调用无副作用；失败后的明确重试应能再次尝试撤回。

## 8. 按什么顺序落地

当前代码已经提供 Core、能力注册表、插件依赖和事件，以及主题插件与通用运行实例；新增部分应在这些基础上接入。

| 当前位置 | 已有行为 | 按本设计需要增加或改变的内容 |
| --- | --- | --- |
| [PluginContext](/Users/yinzhenpu/projects/Lodestory/packages/sdk/src/Plugin.ts) | SDK 公开提供能力、查询能力、订阅和发布事件的契约 | 提交归属插件的通用扩展项 |
| [EngineCore](/Users/yinzhenpu/projects/Lodestory/src/plugin-core/EngineCore.ts) | 单插件能力与订阅暂存、批量回滚、逆序停止 | 扩展项批次提交、停用前撤回、撤回失败保留依赖 |
| 通用 UI 插件 | 尚不存在 | 类型化位置、UI 登记表、快照校验、React 挂载及卸载确认 |
| [themePlugin](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/themePlugin.ts) | 提供 `ThemeService` | 在插件内部绑定并贡献 `ThemeProvider` |
| [main.tsx](/Users/yinzhenpu/projects/Lodestory/src/main.tsx) | 手工组装 Provider 和 `App` | 选择插件集合，调用通用 UI 挂载能力，统一处理失败 |
| [createAppRuntime](/Users/yinzhenpu/projects/Lodestory/src/app/createAppRuntime.ts) | 通用创建与停止；停止 Promise 一直缓存 | 接入安全停止协议，区分并发清理与失败后的重试 |
| 主题使用方 | `useTheme`、设置页面仍直接使用 `themeStore` | 改为使用主题插件公开的能力入口，并声明所属插件的依赖 |

实施顺序由依赖关系决定：

1. 先定义通用扩展项的提交、撤回与失败语义。没有这一步，UI 登记无法随插件安全回滚和停用。
2. 在此基础上实现通用 UI 插件及根位置，确定组件参数、数量、作用范围和排列约定。内核仍不接触 React 类型。
3. 再让主题、右键菜单和应用外壳分别贡献 UI，替换入口中的具体组件组装。此时才能验证同一协议可以接入不同功能。
4. 由布局插件公开具体区域，让设置、编辑器等功能按需要逐步接入；同时把消费者改为读取能力契约。
5. 最后接通窗口关闭、启动失败和 HMR 的统一停止流程，并验证失败保留与重试。

验收应覆盖正常装配、组件参数与稳定实例 ID、缺失或冲突的声明、批次后段失败不呈现 UI、组件清理时服务仍可用、撤回失败不释放服务，以及根结构变化前保存失败时保留原界面。仅看到主题颜色正常，不能证明这些生命周期规则成立。
