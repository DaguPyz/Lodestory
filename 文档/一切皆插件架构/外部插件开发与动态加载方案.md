# 外部插件开发与动态加载方案

**状态：公开 SDK 契约包已实现（ESM、类型声明与独立打包）；跨包稳定 ID、外部包加载、热安装和市场待实施｜日期：2026-10-12**

所属主文档：[一切皆插件架构](../一切皆插件架构.md)。相关设计：[UI 插件化设计](./UI插件化设计.md)。

目标是让开发者在项目之外独立编写插件，用户安装插件后立即使用，不修改应用源码、不重新构建或重新加载应用，同时保留正在编辑的文稿、标签和页面状态。

实现顺序是：先建立公开 SDK 和插件包规范，再打通本地包安装、运行中加载及 UI 增量接入，最后让插件市场复用同一套安装能力。市场提供包的来源，插件运行仍由宿主与 Core 管理。

[`@lodestory/sdk`](../../packages/sdk/README.md) 工作区包已提供宿主与插件共用的公开契约、ESM 和类型声明，可独立打包；尚未发布到 npm。下文的跨包稳定 ID、清单字段、外部加载和安装流程仍是设计示意。

## 1 当前已有能力与缺口

页面已经由 `welcome`、`editor`、`settings` 插件分别提供，但 [appPlugins.ts](../../src/app/appPlugins.ts) 仍静态导入插件工厂并手写数组。因此，现在能运行的是编译进应用的插件，安装目录里的新代码还不能自行接入。

| 当前实现 | 已有行为 | 距离外部插件安装即用还缺什么 |
| --- | --- | --- |
| [EngineCore](../../src/plugin-core/EngineCore.ts) | 启动后可调用 `mount/mountAll`，检查依赖、激活插件并回滚失败批次 | 接收外部包形成的插件实例，并配合 UI 贡献提交和清理确认 |
| [AppRuntime](../../src/app/createAppRuntime.ts) | 对外提供 `get/unmount/stop` | 向安装管理部分提供运行中激活入口及包管理 |
| [UI 插件实现](../../src/plugins/ui/uiPlugin.tsx) 与 [UI SDK 契约](../../packages/sdk/src/ui.ts) | 启动前登记页面和 Provider，支持受控撤回页面并保留其他页面 | 运行中增量登记页面；根包装与格式编辑器在线替换 |
| [能力标识](../../packages/sdk/src/ServiceKey.ts)与[事件标识](../../packages/sdk/src/EventKey.ts) | SDK 根入口导出 `createServiceKey`；同 realm 的提供者和使用者从 SDK 导入同一 `Symbol` | 独立插件包之间稳定、可校验的契约标识与版本 |
| [插件 SDK 契约](../../packages/sdk/src/Plugin.ts) | 已抽取插件、上下文、能力与事件的公开类型，支持独立构建和 npm 打包 | 外部调用代理、项目模板、清单校验和调试工具 |

现在的 UI 在 `pluginsReady` 后拒绝新增页面和根包装；受控撤回已登记页面、布局内容和工作台会话资源时可以保留其他页面。仅将静态 `import` 改成动态加载，仍不能满足安装后立即生效的要求。

## 2 外部作者通过 SDK 开发

作者无法依赖宿主源码的目录结构，也不应随着内部重构修改自己的插件。因此，宿主已将同 realm 的公开契约抽取到工作区包 `@lodestory/sdk`。它尚未提供外部加载客户端或跨执行环境 RPC；Core 和 `pluginsReady` 仍属于宿主实现，`createAppRuntime` 也不属于 SDK。

SDK 源码目前导出插件生命周期、上下文、能力与事件契约（根入口），页面登记与导航契约（`@lodestory/sdk/ui`），以及主题能力契约（`@lodestory/sdk/theme`）。宿主和内置插件在同一 JavaScript realm 内导入这些定义；外部客户端、权限调用代理和跨包标识协议仍待实现。`@lodestory/sdk/ui` 是当前宿主内 React `UiService` 的契约，不是外部 HTML 页面入口，也不支持 `pluginsReady` 后热登记。

外部插件最终可以按下列公开入口编写；这只是契约导入，不代表外部包加载或在线激活已经可用：

```ts
import type {Plugin, PluginContext} from "@lodestory/sdk";
import {uiKey} from "@lodestory/sdk/ui";
import {themeKey, type ThemeService} from "@lodestory/sdk/theme";
```

配套工具负责创建示例项目、检查清单、构建与打包，以及在开发宿主中调试。作者的实际流程是：

目标流程是：**创建独立插件项目 → 安装 SDK → 实现入口与页面 → 本地调试 → 打包 → 交付插件包。**示例模板、外部客户端与打包工具尚未实现。

外部加载完成后，作者只需导入 SDK 并交付插件包，无须向 `appPlugins.ts` 提交代码。

### 能力标识与版本

同一 JavaScript realm 内，宿主与内置插件现从 SDK 导入共享的 `uiKey`、`themeKey` 等标识。每次调用 `createServiceKey("同一个名字")` 仍会生成新的 `Symbol`；名字相同不代表能力相同。独立构建的外部插件若把 SDK 或 `uiKey` 源码复制并打包进去，可能得到另一个标识。SDK 源码抽取没有解决跨包或跨执行环境的稳定匹配，事件也有同样问题。

因此，外部协议使用带命名空间和契约版本的稳定 ID，例如 `lodestory/ui@1`。宿主先检查兼容范围，再把这个外部 ID 匹配到自己持有的能力标识或调用入口；`Symbol` 留在宿主内部，不跨执行环境传递。

插件版本、SDK 版本、能力契约版本分别校验。两个插件之间共享自定义能力时，也必须采用同一份公开契约，不能仅凭名称相同就认为接口兼容。

## 3 插件包说明入口与依赖

宿主拿到包之后，需要先知道它属于谁、如何运行、需要哪些能力，才能决定是否加载。所以每个插件包都必须带清单、编译后的入口和所需资源。

清单至少记录：

- 唯一插件 ID、名称和插件版本。
- SDK 与宿主 API 的兼容范围。
- 代码入口、页面入口及资源位置。
- 依赖的插件 ID 和版本范围，以及要求和提供的能力契约。
- 申请的权限，例如读取当前项目文档。

包的摘要和发行者验证信息用于检查完整性与来源，不能替代代码隔离。

包结构可以包含 `manifest.json`、`dist/plugin.js` 和 `ui/index.html`。具体封装格式在 SDK 和打包工具阶段统一；运行时读取的是已构建产物，不现场安装作者的开发依赖或编译源码。

第一版外部代码支持 JS/TS 构建产物与 Web UI。文件等原生操作通过 SDK 调用宿主能力；任意原生代码扩展需要另行确定运行方式。

## 4 用清单与安装记录找到插件

清单解决了如何识别一个包，但应用还需要知道哪些包应该运行。因此，宿主启动时读取内置插件清单和已安装、已启用的外部插件记录。

内置清单可由构建流程生成；安装记录保存插件 ID、实际安装版本、包位置、启用状态、授权和校验信息。安装新插件改变这些记录，不再修改业务插件数组。

这里必须分清两个动作：

1. **宿主发现和加载包。**根据记录找到包，检查清单与兼容性，在选定的执行环境中加载入口，形成 Core 能管理的插件实例。
2. **Core 激活插件。**接收这些实例，继续按能力依赖检查、排序，并调用 `activate`；失败时清理本批新增的插件。

加载部分属于宿主的启动与执行设施，由宿主创建并持有。它先找到插件，Core 才能管理插件，所以不能要求一个尚未加载的外部插件先提供这项基础能力。

管理插件的业务和市场页面则可以作为普通插件实现，调用宿主公开的安装能力。Core 不处理下载、解压或市场页面，也不识别欢迎页、编辑页等具体业务。

## 5 外部代码通过受控入口运行

独立插件包会执行作者提供的代码，模块加载时就可能运行顶层逻辑，不能把 `activate` 当作代码第一次执行的时刻。因此，执行环境与权限边界必须在加载外部模块之前建立。

`requires/provides` 只检查依赖关系，不会限制任意 JavaScript 访问全局对象或 DOM。Tauri 的权限主要按窗口或 WebView 配置，也不能直接等同于包内某个 JavaScript 插件的权限。[Tauri 权限说明](https://v2.tauri.app/security/capabilities/)

面向第三方市场，方案采用独立、受控的执行入口：宿主为外部插件创建执行环境，插件通过 SDK 发送请求，宿主识别请求所属插件，检查授权与数据范围，再调用已有能力并返回结果。

宿主按公开契约校验请求参数，不能仅相信插件传来的类型、插件 ID 或绝对文件路径；请求身份由宿主建立的连接确认，文件操作限制在实际授权范围内。

外部 UI 提交自己的页面入口，由宿主提供受限视图容器；不直接将外部作者的任意 React 组件函数放进主窗口的 React 树。主题和业务数据通过公开接口传入。内置页面可以保留当前 React 接入方式，两种来源都由 Core 管理对应插件实例。

Worker、独立进程和受限视图容器的具体组合，需要在 Tauri 上验证后确定。分线程或分进程本身不保证完整权限隔离；身份校验、原生调用范围、资源访问与网络权限需要一起落实。仅增加 SDK 包、清单或签名不能完成这一步。

## 6 UI 在现有根节点中增量接入

用户要求安装后立即生效并保留编辑状态，所以不能通过重新加载应用、重发 `pluginsReady` 或重新创建 React 根节点接入新插件。

新流程是：插件激活时提交自己的页面与入口，宿主将这些贡献按插件归属暂存；本次依赖批次全部激活成功、贡献校验通过后，再统一提交。UI 接收到新快照，在已经挂载的页面容器中增加新内容。

已有页面的 ID、组件类型和 React key 保持稳定，编辑页继续挂在原来的树中。用户切到新插件页面时只隐藏编辑页，返回后仍使用同一个编辑实例，文稿、标签和页面状态不需要重新创建。

页面登记必须配套可使用的入口，例如插件管理页面中的打开按钮或宿主公开的导航入口。仅登记一个无法到达的页面，不算安装后可用。

### 全局 Provider 保持稳定

全局 Provider 增删或改变嵌套顺序可能重建已有子树，所以外部插件不能通过重组根包装层实现热安装。

主题等全局服务通过现有能力更新。插件专用的 Provider 放在自己的页面内部，随自己的 UI 管理。全局 `addWrapper` 与运行中页面登记采用不同的生命周期规则，不把当前登记限制整体删除后就视为完成热加载。

### 失败只撤销本批新增内容

贡献在整批激活期间暂存，避免前面的插件已经显示 UI，后面的依赖却激活失败。失败时撤销本批新增贡献、能力和订阅，已经运行的插件和编辑页面继续保留。

外部页面加载或执行失败时，宿主在该插件自己的视图容器内显示错误并记录失败，不复用清空整个应用根节点的启动失败处理。隔离环境中的失败通过受控通道报告，避免把插件错误扩散为当前编辑页的停止。

Core 回滚能力和订阅，不会自动撤销文件写入或远程请求。插件初始化中的外部副作用必须有明确的事务、补偿或恢复方式，不能将 Core 回滚描述为业务操作全部撤销。

## 7 点击安装后的实际流程

插件管理界面调用同一套宿主安装能力，本地包与未来市场下载包都进入下面的流程。

1. 宿主取得插件包，写入暂存位置，校验清单、包完整性、兼容范围、入口与资源路径。
2. 宿主解析插件和能力依赖，确认申请权限及授权范围；加载前检查当前运行环境能否满足要求。
3. 加载部分在受控环境中加载入口，创建 Core 能管理的插件实例。
4. AppRuntime 将本批新增实例交给 Core，Core 按依赖顺序激活；UI 贡献仍保持暂存。
5. 激活成功后，宿主提交 UI 贡献，让现有根节点增量显示插件入口。
6. 宿主将已安装、已启用的版本及授权写入安装记录，安装界面显示可使用状态。

**取得包 → 校验与授权 → 加载入口 → Core 激活 → 提交 UI → 记录启用状态。**

任何阶段失败，都不能显示安装成功。运行时提交与安装记录需要有失败恢复规则；若落盘失败，应撤销本次启用或明确标记待恢复，不能留下“实际已运行但记录为未安装”的无主插件。

重新启动应用时，宿主读取已提交的安装记录并按同一规则恢复插件。安装过程不依赖重新启动，但持久记录保证下一次启动仍能找到已安装插件。

## 8 停用卸载与更新

安装可以增加新内容，但停用正在使用的插件可能涉及未保存数据。因此，先检查依赖和该插件当前使用状态，再执行清理。

宿主先完成必要的保存或处理退出条件；保存失败则保留插件和页面。能够停用时，UI 先退出该插件的页面并撤回它自己的贡献，确认组件清理后，Core 再停止它提供的服务和订阅。其他插件的页面与编辑状态不随之卸载。

撤销贡献要按插件归属处理，不能允许一个插件撤销另一个插件的 UI。若仍有组件消费相关服务，UI 撤回失败时应保留服务，不能继续释放提供者。

当前 Core 在撤回准备失败时保留插件和依赖，AppRuntime 可重试该阶段；`deactivate` 抛错后仍会撤销插件记录和能力，AppRuntime 保留该停止结果。外部包卸载还需要包状态、更新和失败恢复协议；清理失败时保留包和用户数据，记录待恢复状态，不按正常卸载删除目录。

更新沿用同一套校验和加载能力，并锁定新旧版本。更新或卸载插件包与删除用户数据分开处理，不默认删除文稿。正在使用的插件如何保存和恢复自己的状态，应纳入更新协议，不能靠卸载整棵应用树解决。

## 9 插件市场复用安装能力

SDK 与本地包安装跑通后，市场提供搜索、插件介绍、版本和兼容信息、包下载地址，以及发行者和校验信息。用户点击安装时，市场界面把选定的包交给已有安装能力，不另建一条绕过校验、授权或 Core 的运行路径。

这样，本地安装和市场安装具有相同的立即生效、失败回滚和状态保留行为。市场界面本身也是插件，具体展示逻辑不进入通用运行时。

## 10 实施顺序与验收

| 顺序 | 要完成的内容 | 验收结果 |
| --- | --- | --- |
| 1 | SDK 契约、插件包清单、独立仓库示例和开发工具 | 作者不引用宿主 `src`，能够独立构建可校验的包；能力标识与版本能正确匹配 |
| 2 | 外部执行环境、受控 SDK 调用与加载部分 | 外部包能形成 Core 管理的插件实例；未授权请求不能绕过宿主接口执行 |
| 3 | AppRuntime 动态入口、贡献暂存提交、UI 增量装卸及清理确认 | 运行中新增和撤回页面不重建根节点、全局 Provider 或已有编辑实例 |
| 4 | 本地包安装、安装记录及失败恢复 | 打开文稿后安装独立插件，插件立即可用；返回时文稿、标签和编辑状态保留 |
| 5 | 停用卸载、版本更新及恢复验证 | 保存失败或清理失败不会按成功卸载删除包与用户数据；更新状态可追踪 |
| 6 | 市场页面、检索和下载来源 | 一键安装调用同一套安装能力，不要求修改应用源码或重新构建 |

核心验证场景是：保持一份正在编辑的文稿 → 安装来自独立仓库的插件 → 打开插件页面 → 返回编辑页 → 确认同一个编辑实例、文稿和标签仍在。

还需验证：插件依赖不兼容、包校验失败、批次后段激活失败、权限请求越界、安装记录写入失败，以及 UI 撤回或插件清理失败。这些情况只影响相应的新插件或操作，不通过重新加载应用丢弃现有编辑状态。
