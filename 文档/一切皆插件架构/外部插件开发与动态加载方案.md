# 外部插件开发与动态加载方案

**状态：公开 SDK 契约包已实现（ESM、类型声明与独立打包）；跨包稳定 ID、外部包加载、热安装和市场待实施｜日期：2026-10-12**

**最新进展：**已加入独立程序后端的最小加载插件与宿主进程桥接，提供启动、调用和退出能力；已在桌面应用中与测试用 Rust 后端验证启动、调用、错误返回和退出。测试程序不是完整第三方插件；插件包发现与安装、外部前端接入和动态库加载仍未实现。

所属主文档：[一切皆插件架构](../一切皆插件架构.md)。相关设计：[UI 插件化设计](./UI插件化设计.md)。

目标是让开发者借助脚手架在项目之外独立编写插件，并将前端内容与 Rust 后端一起交付为完整插件包。用户可手动导入或通过插件市场安装；安装后立即使用，不修改应用源码、不重新构建或重新加载应用，同时保留正在编辑的文稿、标签和页面状态。插件可以只包含前端、只包含后端，或同时包含两者。

实现顺序是：先建立公开 SDK 和插件包规范，再打通本地包安装、运行中加载及 UI 增量接入，最后让插件市场复用同一套安装能力。市场提供包的来源，插件运行仍由宿主与 Core 管理。

[`@lodestory/sdk`](../../packages/sdk/README.md) 工作区包已提供宿主与插件共用的公开契约、ESM 和类型声明，可独立打包；尚未发布到 npm。下文的跨包稳定 ID、清单字段、外部加载和安装流程仍是设计示意。

## 1 当前已有能力与缺口

页面已经由 `welcome`、`editor`、`settings` 插件分别提供，但 [appPlugins.ts](../../src/app/appPlugins.ts) 仍静态导入插件工厂并手写数组。因此，现在能运行的是编译进应用的插件，安装目录里的新代码还不能自行接入。

| 当前实现 | 已有行为 | 距离外部插件安装即用还缺什么 |
| --- | --- | --- |
| [EngineCore](../../src/plugin-core/EngineCore.ts) | 启动后可调用 `mount/mountAll`，检查依赖、激活插件并回滚失败批次 | 接收外部包形成的插件实例，并配合 UI 贡献提交和清理确认 |
| [AppRuntime](../../src/app/createAppRuntime.ts) | 对外提供 `get/unmount/stop` | 向安装管理部分提供运行中激活入口及包管理 |
| [UI 插件实现](../../src/plugins/ui/uiPlugin.tsx) 与 [UI SDK 契约](../../packages/sdk/src/ui.ts) | 启动前登记页面和 Provider，支持受控撤回页面并保留其他页面 | 运行中增量登记页面；根包装与格式编辑器在线替换 |
| [能力标识](../../packages/sdk/src/ServiceKey.ts)与[事件标识](../../packages/sdk/src/EventKey.ts) | SDK 根入口导出 `createServiceKey`；同 realm 的提供者和使用者从 SDK 导入同一 `Symbol` | 独立插件包之间稳定、可校验的契约标识与版本 |
| [插件 SDK 契约](../../packages/sdk/src/Plugin.ts) | 已抽取插件、上下文、能力与事件的公开类型，支持独立构建和 npm 打包 | 外部调用代理、项目模板、清单校验和调试工具 |

现在的 UI 在 `pluginsReady` 后拒绝新增页面和根包装；受控撤回已登记页面、布局内容和工作台会话资源时可以保留其他页面。仅将静态 `import` 改成动态加载，仍不能满足安装后立即生效的要求。

## 2 外部作者通过 SDK 开发

作者无法依赖宿主源码的目录结构，也不应随着内部重构修改自己的插件。因此，宿主已将同 realm 的公开契约抽取到工作区包 `@lodestory/sdk`。它尚未提供外部加载客户端或跨执行环境 RPC；Core 和 `pluginsReady` 仍属于宿主实现，`createAppRuntime` 也不属于 SDK。

SDK 源码目前导出插件生命周期、上下文、能力与事件契约（根入口），页面登记与导航契约（`@lodestory/sdk/ui`），以及主题能力契约（`@lodestory/sdk/theme`）。宿主和内置插件在同一 JavaScript realm 内导入这些定义；外部客户端和跨包标识协议仍待实现。`@lodestory/sdk/ui` 是当前宿主内 React `UiService` 的契约，不是外部 HTML 页面入口，也不支持 `pluginsReady` 后热登记。

外部插件最终可以按下列公开入口编写；这只是契约导入，不代表外部包加载或在线激活已经可用：

```ts
import type {Plugin, PluginContext} from "@lodestory/sdk";
import {uiKey} from "@lodestory/sdk/ui";
import {themeKey, type ThemeService} from "@lodestory/sdk/theme";
```

配套工具负责创建示例项目、检查清单、构建与打包，以及在开发宿主中调试。作者的实际流程是：

目标流程是：**创建独立插件项目 → 安装 SDK → 实现入口与页面 → 本地调试 → 打包 → 交付插件包。**示例模板、外部客户端与打包工具尚未实现。

外部加载完成后，作者只需导入 SDK 并交付插件包，无须向 `appPlugins.ts` 提交代码。

### 能力标识与版本

同一 JavaScript realm 内，宿主与内置插件现从 SDK 导入共享的 `uiKey`、`themeKey` 等标识。每次调用 `createServiceKey("同一个名字")` 仍会生成新的 `Symbol`；名字相同不代表能力相同。独立构建的外部插件若把 SDK 或 `uiKey` 源码复制并打包进去，可能得到另一个标识。SDK 源码抽取没有解决跨包或跨执行环境的稳定匹配，事件也有同样问题。

因此，外部协议使用带命名空间和契约版本的稳定 ID，例如 `lodestory/ui@1`。宿主先检查兼容范围，再把这个外部 ID 匹配到自己持有的能力标识或调用入口；`Symbol` 留在宿主内部，不跨执行环境传递。

插件版本、SDK 版本、能力契约版本分别校验。两个插件之间共享自定义能力时，也必须采用同一份公开契约，不能仅凭名称相同就认为接口兼容。

## 3 插件包说明入口与依赖

宿主拿到包之后，需要先知道它属于谁、如何运行、需要哪些能力，才能决定是否加载。所以每个插件包都必须带清单、编译后的入口和所需资源。

清单至少记录：

- 唯一插件 ID、名称和插件版本。
- SDK 与宿主 API 的兼容范围。
- 代码入口、页面入口及资源位置。
- 依赖的插件 ID 和版本范围，以及要求和提供的能力契约。

包的摘要和发行者验证信息用于检查完整性与来源，不能保证插件代码安全。

包结构可以包含 `manifest.json`、`dist/plugin.js` 和 `ui/index.html`。具体封装格式在 SDK 和打包工具阶段统一；运行时读取的是已构建产物，不现场安装作者的开发依赖或编译源码。

外部插件目标支持 JS/TS 构建产物、Web UI 和编译后的 Rust 后端。文件等宿主能力通过公开接口调用；Rust 后端的产物形式、运行方式与调用协议尚待技术验证，不能假定 Tauri 会自动加载外部 Rust 插件。

### 3.1 平台构建与匹配

确定的方向是：同一插件按其支持的目标平台分别构建对应版本，宿主安装时选择兼容版本。包含 Rust 后端时，构建目标不仅包括 macOS、Windows 或 Linux，还包括处理器架构，以及需要时的运行环境和系统版本。例如 macOS 的 Apple 芯片和 Intel 芯片可能需要不同产物，因此不能固定假设一个插件只有三个平台版本。前端资源是否能共用，由其实际依赖的平台能力决定。

脚手架与打包工具负责生成所需目标的构建产物，并在清单中声明每个产物的适用范围。清单字段、版本比较规则和具体打包格式尚待定义；交付可以采用各平台独立的包，也可以在一个包中包含多个平台产物，具体方式尚未决定。

宿主安装时根据当前应用和运行环境选择兼容产物，并在执行任何插件代码前检查平台、处理器及清单声明的其他兼容条件；找不到兼容产物时拒绝安装或启用并说明原因。手动导入和未来市场安装共用这套匹配规则。平台匹配不代表宿主已经能够运行或调用该后端，还必须单独确定并验证执行方式、前后端通信、权限边界及宿主接口版本。

未来插件市场按当前设备的操作系统、处理器架构及其他适用的兼容条件筛选，只展示有兼容版本的插件，并下载适合当前设备的产物。例如 Apple 芯片的 Mac 展示可在该设备运行的插件版本。展示筛选不能代替安装和启用前的兼容性检查；市场筛选与下载能力尚未实现。

不同目标的构建可能需要相应平台的工具链或构建环境；脚手架负责提供一致的构建流程，不承诺任意开发机器都能直接生成全部平台产物。插件发布前仍需在支持的平台上验证安装、运行和停用。

### 3.2 脚手架与宿主的统一接口草案

统一接口不是单个函数，而是双方共同遵守的三层约定。清单结构已确认，具体校验规则与相关接口细节仍需设计，且尚未实现。

**已确认的插件身份信息：**清单包含插件 ID、名称和版本。插件 ID 使用字符串，由开发者命名空间与插件名组成，例如 `com.example.timeline`；同一插件的不同版本沿用同一个 ID，版本单独记录。名称供用户识别，可以修改，也不要求全局唯一。命名空间本身不证明发行者身份，ID 归属、发行者验证和 ID 字符规则待后续设计。

插件版本采用[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)，例如 `1.2.3`：修复兼容的问题递增修订号，新增向后兼容的功能递增次版本号，不兼容的公开接口变更递增主版本号。预发布版本和构建元数据遵循该规范；初始开发阶段的 `0.y.z` 不承诺公开接口稳定。插件支持的宿主接口版本范围在清单中单独声明，不从插件自身的版本号推断。

**已确认的清单结构：**以下插件、能力 ID 和版本均为示例；注释仅用于说明，正式清单是否允许注释尚未确定。

```jsonc
{
  "manifestVersion": "1.0",          // 清单格式版本
  "id": "com.example.timeline",      // 插件唯一 ID
  "name": "时间线",                   // 展示给用户的插件名称
  "version": "1.0.0",                // 插件自身版本
  "description": "管理故事时间线",     // 插件功能简介
  "compatibility": {                  // 插件运行所需的兼容条件
    "hostApi": "^1.0.0",             // 支持的 Lodestory 接口版本范围
    "react": "^19.0.0"               // 支持的 React 版本范围；没有前端时可省略
  },
  "dependencies": {                  // 插件的依赖和能力声明
    "plugins": [                     // 依赖的其他插件
      {
        "id": "com.example.story-data", // 依赖的插件 ID
        "version": "^1.0.0"             // 支持该插件的版本范围
      }
    ],
    "requires": [                    // 需要使用的公开能力
      {
        "id": "com.example.story-data.stories", // 能力 ID
        "version": "^1.0.0"                    // 支持的能力接口版本范围
      }
    ],
    "provides": [                    // 本插件提供的公开能力
      {
        "id": "com.example.timeline.timelines", // 能力 ID
        "version": "1.0.0"                      // 提供的能力接口版本
      }
    ]
  },
  "frontend": {                      // 前端信息；没有前端时可省略
    "entry": "dist/frontend/index.js" // 插件包内的前端入口文件
  },
  "backend": {                       // 后端信息；没有后端时可省略
    "type": "process",               // process：独立程序；dynamic-library：动态库
    "artifacts": [                   // 各平台对应的后端运行文件
      {
        "os": "macos",               // 操作系统
        "arch": "arm64",             // 处理器架构
        "entry": "dist/backend/macos-arm64/timeline" // 后端入口文件
      },
      {
        "os": "windows",             // 操作系统
        "arch": "x64",               // 处理器架构
        "entry": "dist/backend/windows-x64/timeline.exe" // 后端入口文件
      }
    ]
  }
}
```

没有依赖或能力时，对应列表可以为空。清单不要求权限申请字段；前端和后端可以各自省略，但至少包含其中一项。示例结构允许一个包包含多个平台产物，也允许按平台分别打包；实际交付方式仍未决定。能力 ID 的命名和匹配、版本范围的具体规则、字段校验与包格式仍需细化，并协调上文以 `lodestory/ui@1` 表示的稳定能力标识；当前均尚未实现。

**已确认的前端入口原则：**插件包含前端时，清单记录指向插件包内文件的入口，供 Lodestory 查找前端加载的起点。入口路径的校验规则、文件类型和加载方式尚待确定；脚手架开发时的构建入口不一定与交付包中的加载入口相同。

**已确认的前端技术栈：**外部插件界面统一使用 React 开发，脚手架围绕这一约定提供开发与构建支持。Lodestory 提供一个明确版本的 React 实例，加载插件时向其提供同一实例，避免每个插件各自携带和运行一份。插件清单声明支持的 React 版本范围；宿主加载前检查自己提供的版本是否在范围内，不在范围则拒绝加载并说明原因。插件开发时使用的 React 版本不要求相同，插件开发者负责确保插件能在其声明范围内及宿主提供的版本上运行；构建时使用的版本不能自动证明整个范围兼容，需要相应测试。主应用升级 React 后，如新版本不在插件声明的范围内，插件需要适配并重新发布。具体的共享模块机制、构建约束及插件隔离仍需设计和验证，当前尚未实现。

脚手架由 Lodestory 维护基础依赖配置；默认使用与其面向的 Lodestory 版本一致的 React 等共享依赖版本，帮助开发者从兼容环境开始。默认对齐不改变兼容范围规则，也不要求插件自行携带的普通依赖或构建工具与宿主完全相同；脚手架与宿主版本之间的对应和更新规则待设计。

**已确认的前端界面方向：**外部插件可以贡献完整页面，也可以贡献工作台内的面板等内容。插件通过公开登记契约描述其内容和用途，导航或布局实现决定入口和呈现位置，插件不直接指定宿主的固定位置。当前完整页面及其导航由 UI 与导航布局协作管理，工作台内的内容由布局服务管理；外部 React 插件如何接入这些契约仍需设计与验证，运行中新增页面尚未实现。

**已确认的样式与主题原则：**推荐插件使用 Lodestory 公开的主题变量，使界面能够随应用主题变化；这不是强制要求，插件也可以自行指定样式。推荐开发者控制样式作用范围，避免影响应用和其他插件，但由开发者自行负责，宿主不强制限定或保证样式隔离，因此插件的全局样式可能影响其他界面。共享 React 本身不提供样式隔离。

不再选用 Shadow DOM 作为外部插件的强制接入方案，也不为此要求现有弹框和下拉框适配。此前的本机原型验证表明 Shadow DOM 可以隔离示例样式并继承主题变量，但现有共享 Dialog 和 Select 的弹出内容默认位于隔离区域之外，需要适配才能在该区域使用；这只是探索记录，不代表当前方案需要实施或已经实现。样式约定不等于插件代码的安全隔离。

插件安装并启用后，先检查 React 等兼容条件，再加载插件入口并登记其界面；界面可被用户找到，但不因为安装就立即打开。界面采用懒加载：用户首次打开页面或面板时才加载其界面代码并创建组件；切换到其他界面时保留已创建的组件与状态，返回后继续使用。插件入口用于登记，与界面代码的拆分方式待设计；当前默认布局并不普遍具备上述懒加载行为，外部插件接入需要实现并验证。

工作台内容应遵循[现有布局公开契约](../../packages/sdk/src/layout.ts)：登记内容的标识、标题、用途和渲染内容，可提供图标与排序；用途表示内容的作用，不代表固定位置，布局实现决定具体呈现。应用级页面遵循 [UI 和导航布局契约](../../packages/sdk/src/navigation-layout.ts)，不将完整页面误当作工作台布局内容。外部插件的动态加载与跨包对接尚未实现，现有接口不自动等于外部插件已能使用。

1. **插件包契约：安装前识别。**脚手架和打包工具生成清单及对应运行文件；宿主安装器按同一规则读取和校验。清单需要表达插件 ID、名称、插件版本、清单格式版本、兼容的宿主接口版本、插件或能力依赖，以及前端和后端的入口与资源。Rust 后端还须声明各产物适用的平台；无前端或无后端时，不要求不存在部分的入口。包结构、字段语法及完整性校验规则待确定。
2. **生命周期契约：加载、激活与停用。**宿主在执行外部代码前完成清单与兼容性检查，建立执行环境，再按约定加载入口和激活插件；插件通过公开接口登记自身能力与界面贡献。批次成功后才提交新增贡献，失败时撤销本次已登记内容并清理资源。停用时复用检查、必要的保存、界面撤回和资源释放流程；保存或撤回失败时保留相应插件及用户内容。安装记录与运行状态的提交、崩溃恢复及清理失败处理还须细化。
3. **运行通信契约：插件工作时协作。**插件前端调用应用能力、前端与自身 Rust 后端通信，都通过版本化的公开接口完成。传输方式、消息的具体格式、错误码清单及跨环境能力标识待进一步设计和技术验证，不能直接把当前同一 JavaScript 环境里的 SDK 对象当作跨环境协议。

插件前端调用自身后端时，开发者接口应尽量简单，目标是接近普通函数调用；具体如何定义接口、传递请求与结果，以及后端如何运行，仍需设计和验证，不能视为已经实现。

外部 Rust 后端确定同时支持两种形式：由宿主启动独立程序，或由宿主加载动态库；WebAssembly 不纳入当前方案。插件清单声明采用的形式及入口，宿主按形式选择对应的加载和退出方式；插件前端尽量使用统一的调用接口。独立程序加载已有最小实现，尚未与真实第三方插件联调；动态库形式尚未实现。跨平台构建、完整生命周期和故障处理均仍需验证。动态库与应用在同一进程中，严重错误可能影响应用，其代码可能使用应用已有的系统权限；独立进程有助于隔离崩溃，但默认不自动限制权限。

目标是后端加载与退出采用统一公开契约，由独立程序加载实现和动态库加载实现分别提供；这两个加载实现作为内置插件装配，并在加载外部插件前启动。它们通过宿主提供的原生设施执行各自操作，按插件清单声明的形式选择实现；通用 Core 不识别具体后端形式。目前仅独立程序加载插件已装配并提供专用 SDK 能力，尚未实现两种形式的统一选择接口或清单加载。

加载时，调用方依据已校验的插件清单提供后端形式与入口，由相应内置加载实现处理。成功后返回统一的可操作运行实例，供后续调用和退出使用；它是调用方持有的操作入口，不一定是后端自身的对象，独立进程的实现需负责转发请求和结果。加载失败返回错误，不将插件标记为成功启用，并清理部分初始化的资源；若清理失败，须报告并保留可追踪状态。接口参数、实例具体类型及清理失败的恢复规则尚待设计。

**插件前端调用自身后端的约定：**通过运行实例的统一调用接口，传入操作名、Schema 版本、参数内容和请求 ID。操作名标识要执行的后端逻辑，可由插件扩展；Schema 版本标识参数结构的版本，参数按预先定义的结构传递；请求 ID 标识本次调用，用于追踪和对应结果。后端执行后返回结果或错误。

每次调用返回执行状态和对应本次调用的请求 ID，以明确区分成功与失败。成功时还返回执行结果；操作无须返回数据时，执行结果留空，仍返回成功状态和请求 ID。失败时还返回平台统一定义的错误码，以及由插件开发者提供具体说明的错误信息。

请求和返回字段的具体格式、执行结果的结构及留空表示方式、版本兼容规则、错误码清单与传输机制仍需细化和验证；上述约定尚未实现。该调用约定处理插件前端与自身后端之间的通信，不替代插件之间通过公开能力协作。

**独立程序通信协议：**前端通过统一的运行实例调用后端，独立程序加载插件负责启动进程、发送请求并接收结果；使用标准输入和标准输出传递逐行 JSON 消息，每行一条。标准输出仅用于协议消息，插件日志写入标准错误输出。消息的 `type` 用于区分用途。

后端初始化完成后主动发送 `{"type":"ready","protocolVersion":"1.0.0"}`；加载插件检查是否支持该协议版本，通过后才返回运行实例，不支持则加载失败并清理已启动进程。该版本用于约定双方的通信消息，与调用参数的 `schemaVersion` 分开；当前是版本检查而非自动协商，兼容与升级规则待设计。

调用请求示例：`{"type":"call","requestId":"req-001","operation":"getTimeline","schemaVersion":"1.0.0","params":{"timelineId":"timeline-1"}}`。成功返回示例：`{"type":"response","requestId":"req-001","status":"success","result":{"name":"第一卷时间线"}}`；没有业务数据时 `result` 为 `null`。失败返回示例：`{"type":"response","requestId":"req-001","status":"error","error":{"code":"PLUGIN_OPERATION_FAILED","message":"找不到指定时间线"}}`，其中错误码仅作示例，实际清单待确定。多个调用可同时进行，按请求 ID 关联返回，不要求按发出顺序返回。

退出时发送 `{"type":"shutdown","requestId":"shutdown-001"}`；后端停止工作并完成清理后，返回 `{"type":"response","requestId":"shutdown-001","status":"success","result":null}`，然后正常结束进程。平台确认进程结束后才标记退出成功；清理失败返回错误，等待超时或退出失败按下文退出规则处理。进程意外结束时，尚未完成的调用返回错误，平台不自动重试，以免重复执行操作。独立程序加载器的最小协议处理已实现，并已在桌面应用中与测试用 Rust 后端联调。

当前窗口关闭已接入插件停止流程：工作台检查和保存通过后，独立程序加载器通知它管理的后端退出；失败或超时会保留窗口并提示重试。后端若返回退出错误并允许重试，须继续运行并接收后续退出请求；超时重试继续等待原有请求，不强制终止进程。

**动态库调用方向：**前端继续使用统一运行实例；动态库加载插件通过动态库公开的 C 接口调用后端，沿用相同的业务请求和返回结构。动态库提供初始化、调用、退出及释放返回数据的入口；加载插件在后台执行调用并接收结果，避免在界面线程中直接运行后端逻辑。退出时先确认已有调用和后台任务结束并清理资源，再卸载动态库；失败时按下文退出规则处理。具体函数签名、数据归属、版本兼容和各平台安全卸载仍需设计与验证，尚未实现。

**后端退出：**参考 IntelliJ 平台的动态插件卸载思路，退出时停止接收新调用，等待已开始的调用结束，并停止后台任务、释放资源；全部完成后才标记退出成功。等待调用或停止后台任务达到 30 秒时提示用户。退出失败时保留可追踪状态，不强行释放仍在使用的资源，也不将插件标记为已成功退出；提示用户重启应用。重启须经过工作台统一离开检查与必要的保存；保存失败时保留用户内容，不自动重启。超时后的具体交互仍待设计；两种后端形式分别需要验证能否安全退出。

外部插件使用其他插件能力时，沿用现有架构原则：声明所需能力，通过公开契约取得并调用，不读取其他插件的私有数据或实现。当前内置插件由内核检查依赖并提供对应服务，取得服务后直接调用其公开方法；外部插件如何连接这些能力和完成版本匹配仍待实现。

Lodestory 为外部开发者提供配套文档，列出允许外部插件依赖的插件和能力、公开 API、使用方法及相关版本要求。脚手架与 SDK 应帮助开发者声明和使用这些公开契约；文档中的对外可用范围需与实际实现一致，不能把现有内部插件拥有的所有接口默认视作已开放给外部插件。

宿主负责发现、校验、加载和运行设施；插件管理界面负责用户操作，并调用宿主公开的安装能力；Core 只负责通用插件生命周期与依赖。手动导入和市场下载作为包的不同来源，进入同一安装流程。

验收以独立脚手架项目为准：构建匹配平台的插件包，应用无需重新构建即可安装、激活并使用；安装期间保持原有文稿与编辑实例，清单不兼容、激活失败或保存失败时不会显示成功或丢失用户内容。

## 4 用清单与安装记录找到插件

清单解决了如何识别一个包，但应用还需要知道哪些包应该运行。因此，宿主启动时读取内置插件清单和已安装、已启用的外部插件记录。

内置清单可由构建流程生成；安装记录保存插件 ID、实际安装版本、包位置、启用状态和校验信息。安装新插件改变这些记录，不再修改业务插件数组。

这里必须分清两个动作：

1. **宿主发现和加载包。**根据记录找到包，检查清单与兼容性，在选定的执行环境中加载入口，形成 Core 能管理的插件实例。
2. **Core 激活插件。**接收这些实例，继续按能力依赖检查、排序，并调用 `activate`；失败时清理本批新增的插件。

宿主创建并持有启动与原生执行设施；外部后端的不同加载实现由预先启动的内置插件通过统一契约提供。加载设施先找到并装载外部插件，Core 才能管理其插件实例，因此不能要求尚未加载的外部插件先提供加载自身的能力。各方的具体接口和生命周期仍待设计。

管理插件的业务和市场页面则可以作为普通插件实现，调用宿主公开的安装能力。Core 不处理下载、解压或市场页面，也不识别欢迎页、编辑页等具体业务。

## 5 外部代码与信任边界

参考 [JetBrains 插件安全模式](https://plugins.jetbrains.com/docs/marketplace/understanding-plugin-security.html)：当前方案不为外部插件提供沙箱或细粒度权限控制。安装和启用插件意味着信任其代码；插件可能以运行账户或应用进程拥有的权限访问文件、网络和其他系统资源。独立进程默认不等于沙箱，动态库与应用共享进程。清单中的依赖声明、公开接口和包校验都不能阻止插件代码直接访问系统资源；此前示例中的权限申请字段不作为已确定的清单要求。

未来插件市场参考 JetBrains 的自动检查、人工审核和发现问题后处理的方式；具体审核规则、执行方式和问题插件处置机制仍待设计，市场尚未实现。审核不能保证插件绝对安全，也不能覆盖未通过市场的手动导入包；手动导入和市场安装如何向用户说明信任风险，仍待设计。

独立插件包加载时就可能执行顶层代码，不能把 `activate` 当作代码第一次执行的时刻。外部插件仍须通过公开契约与其他插件协作；宿主应校验接口输入并处理错误，但不能将这些约定或检查描述为安全隔离。外部 UI 统一使用 React，并以与应用共享 React 为目标；具体接入方式仍待设计与验证。

## 6 UI 在现有根节点中增量接入

用户要求安装后立即生效并保留编辑状态，所以不能通过重新加载应用、重发 `pluginsReady` 或重新创建 React 根节点接入新插件。

新流程是：插件激活时提交自己的页面与入口，宿主将这些贡献按插件归属暂存；本次依赖批次全部激活成功、贡献校验通过后，再统一提交。UI 接收到新快照，在已经挂载的页面容器中增加新内容。

已有页面的 ID、组件类型和 React key 保持稳定，编辑页继续挂在原来的树中。用户切到新插件页面时只隐藏编辑页，返回后仍使用同一个编辑实例，文稿、标签和页面状态不需要重新创建。

页面登记必须配套可使用的入口，例如插件管理页面中的打开按钮或宿主公开的导航入口。仅登记一个无法到达的页面，不算安装后可用。

### 全局 Provider 保持稳定

全局 Provider 增删或改变嵌套顺序可能重建已有子树，所以外部插件不能通过重组根包装层实现热安装。

主题等全局服务通过现有能力更新。插件专用的 Provider 放在自己的页面内部，随自己的 UI 管理。全局 `addWrapper` 与运行中页面登记采用不同的生命周期规则，不把当前登记限制整体删除后就视为完成热加载。

### 失败只撤销本批新增内容

贡献在整批激活期间暂存，避免前面的插件已经显示 UI，后面的依赖却激活失败。失败时撤销本批新增贡献、能力和订阅，已经运行的插件和编辑页面继续保留。

外部插件页面无法加载时，通过应用的系统弹框提示该插件有问题。首版针对插件界面的 React 渲染错误提供局部兜底：在出错的插件界面区域显示错误信息，其他界面和正在编辑的内容保持不变，不以清空整个应用根节点作为错误处理方式。现有默认布局已对每个工作台内容使用错误边界；外部插件接入后仍需验证对应场景，完整页面的边界接入方式也需确认。

首版暂不要求隔离按钮事件、异步任务或阻塞运行等其他错误；React 错误边界不等于完整故障或权限隔离。

Core 回滚能力和订阅，不会自动撤销文件写入或远程请求。插件初始化中的外部副作用必须有明确的事务、补偿或恢复方式，不能将 Core 回滚描述为业务操作全部撤销。

## 7 点击安装后的实际流程

插件管理界面调用同一套宿主安装能力，本地包与未来市场下载包都进入下面的流程。

1. 宿主取得插件包，写入暂存位置，校验清单、包完整性、兼容范围、入口与资源路径。
2. 宿主解析插件和能力依赖，加载前检查当前运行环境能否满足要求。
3. 加载部分加载入口，创建 Core 能管理的插件实例。
4. AppRuntime 将本批新增实例交给 Core，Core 按依赖顺序激活；UI 贡献仍保持暂存。
5. 激活成功后，宿主提交 UI 贡献，让现有根节点增量显示插件入口。
6. 宿主将已安装、已启用的版本写入安装记录，安装界面显示可使用状态。

**取得包 → 校验 → 加载入口 → Core 激活 → 提交 UI → 记录启用状态。**

任何阶段失败，都不能显示安装成功。运行时提交与安装记录需要有失败恢复规则；若落盘失败，应撤销本次启用或明确标记待恢复，不能留下“实际已运行但记录为未安装”的无主插件。

重新启动应用时，宿主读取已提交的安装记录并按同一规则恢复插件。安装过程不依赖重新启动，但持久记录保证下一次启动仍能找到已安装插件。

## 8 停用卸载与更新

安装可以增加新内容，但停用正在使用的插件可能涉及未保存数据。因此，先检查依赖和该插件当前使用状态，再执行清理。

宿主先完成必要的保存或处理退出条件；保存失败则保留插件和页面。能够停用时，UI 先退出该插件的页面并撤回它自己的贡献，确认组件清理后，Core 再停止它提供的服务和订阅。其他插件的页面与编辑状态不随之卸载。

撤销贡献要按插件归属处理，不能允许一个插件撤销另一个插件的 UI。若仍有组件消费相关服务，UI 撤回失败时应保留服务，不能继续释放提供者。

当前 Core 在撤回准备失败时保留插件和依赖，AppRuntime 可重试该阶段；`deactivate` 抛错后仍会撤销插件记录和能力，AppRuntime 保留该停止结果。外部包卸载还需要包状态、更新和失败恢复协议；清理失败时保留包和用户数据，记录待恢复状态，不按正常卸载删除目录。

更新沿用同一套校验和加载能力，并锁定新旧版本。更新或卸载插件包与删除用户数据分开处理，不默认删除文稿。正在使用的插件如何保存和恢复自己的状态，应纳入更新协议，不能靠卸载整棵应用树解决。

## 9 插件市场复用安装能力

SDK 与本地包安装跑通后，市场提供搜索、插件介绍、版本和兼容信息、包下载地址，以及发行者和校验信息。用户点击安装时，市场界面把选定的包交给已有安装能力，不另建一条绕过校验或 Core 的运行路径。

这样，本地安装和市场安装具有相同的立即生效、失败回滚和状态保留行为。市场界面本身也是插件，具体展示逻辑不进入通用运行时。

## 10 实施顺序与验收

| 顺序 | 要完成的内容 | 验收结果 |
| --- | --- | --- |
| 1 | SDK 契约、插件包清单、独立仓库示例和开发工具 | 作者不引用宿主 `src`，能够独立构建可校验的包；能力标识与版本能正确匹配 |
| 2 | 外部执行环境、SDK 调用与加载部分 | 外部包能形成 Core 管理的插件实例，并通过公开契约协作 |
| 3 | AppRuntime 动态入口、贡献暂存提交、UI 增量装卸及清理确认 | 运行中新增和撤回页面不重建根节点、全局 Provider 或已有编辑实例 |
| 4 | 本地包安装、安装记录及失败恢复 | 打开文稿后安装独立插件，插件立即可用；返回时文稿、标签和编辑状态保留 |
| 5 | 停用卸载、版本更新及恢复验证 | 保存失败或清理失败不会按成功卸载删除包与用户数据；更新状态可追踪 |
| 6 | 市场页面、检索和下载来源 | 一键安装调用同一套安装能力，不要求修改应用源码或重新构建 |

核心验证场景是：保持一份正在编辑的文稿 → 安装来自独立仓库的插件 → 打开插件页面 → 返回编辑页 → 确认同一个编辑实例、文稿和标签仍在。

还需验证：插件依赖不兼容、包校验失败、批次后段激活失败、安装记录写入失败，以及 UI 撤回或插件清理失败。相应失败处理不应通过重新加载应用丢弃现有编辑状态；由于插件代码不受沙箱隔离，不能保证恶意代码或严重故障只影响插件自身。
