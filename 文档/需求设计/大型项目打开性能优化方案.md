# 大型项目打开性能优化方案

日期：2026-10-26

状态：第一、第二阶段及剩余冻结停顿优化完成；超大 TXT 的编辑器初始化、首次解码与字数统计优化已实施

优化前，大型项目打开期间会反复解析未变化的数据、反复汇总全部时间线。第一阶段消除这些重复计算；后续加载方式根据复测结果调整。

## 现状与依据

以下问题对应优化前基线 `e3a99959a0d65b8bce374c36c3f64ad3be959adf`，本次实施和复测结果见末节。

当前测试项目包含 26 条时间线、2158 个事件、668 个资产。事件文件共 2,527,609 字节，资产文件为 1,220,058 字节。

上一轮只读模型基准使用真实项目文件，替代原生文件调用，不包含桌面通信、文件树扫描和真实界面渲染：

| 指标 | 优化前实现 | 临时过滤无关通知后的对照 |
| --- | --- | --- |
| 打开项目操作完成 | 约 14.2 秒 | 约 2.1 秒 |
| 文件读取次数 | 79 | 79 |
| 目录查询次数 | 54 | 54 |
| 资产文件解码次数 | 81 | 3 |

对照仅在测量脚本中改变通知过滤，没有修改产品代码。它表明重复计算是主要放大因素；2.1 秒不能作为真实桌面打开耗时或已完成优化的结果。

### 重复计算的形成过程

1. 项目存储读入一个文件，向所有订阅者发布共享快照。
2. 资产、各条时间线的轴和事件模块收到通知，再次解析自己的文件，即使字节没有变化。
3. 时间线元数据集合再次解码已有文件，列表模型再次解析、排序。
4. 轴、事件或列表模型发布更新，时间线插件再次遍历全部条目，逐个扫描事件计算数量和时间范围。
5. 加载下一个文件，再重复上述过程。时间线越多，同一批数据被处理的次数越多。

| 问题 | 当前实现依据 |
| --- | --- |
| 资产在全局文件通知中重新解析整个资产文件，并比较完整数据 | [assetSchemaStore.ts](../../src/plugins/asset-management/assetSchemaStore.ts) 的订阅回调、`acceptFile`、`sameSchema` |
| 每条时间线的轴和事件都会收到全局通知并重新解析；读取返回时还会再次解析 | [timelineAxisStore.ts](../../src/plugins/timeline/timelineAxisStore.ts)、[timelineEventStore.ts](../../src/plugins/timeline/timelineEventStore.ts) 的订阅回调和 `acceptFile` |
| 元数据反复解码、解析和排序 | [timelineListFiles.ts](../../src/plugins/timeline/timelineListFiles.ts) 的 `buildSnapshot`、[timelineListModel.ts](../../src/plugins/timeline/timelineListModel.ts) 的 `buildSnapshot` |
| 每次更新汇总全部时间线；未选中的时间线也立即加载轴和事件 | [timelinePlugin.tsx](../../src/plugins/timeline/timelinePlugin.tsx) 的 `publishSession`、`syncResources`、`createEvents`、`enrichEntry` |

其他成本包括重复目录查询、字节复制、隐藏面板的计算和大列表渲染。它们需要在主要重复计算消除后分别测量，不能把模型基准中的全部耗时归给界面或磁盘。

## 架构归属与接入

| 项目要求 | 本次方案 |
| --- | --- |
| 归属 | `asset-management` 拥有资产解析缓存；`timeline` 拥有元数据、轴、事件及列表摘要缓存。缓存属于派生结果，不另建文件内容缓冲或保存队列。 |
| 协作 | 继续通过 `@lodestory/sdk/project-storage` 的 `ProjectFiles` 读写共享字节；大纲通过 `@lodestory/sdk/timeline` 消费列表。首阶段不新增公开能力，不导入其他插件的私有实现。 |
| 接入 | 保留工作台参与者及 `layout.registerContent` 登记方式，继续由现有插件提供页面内容；入口和插件内核不增加业务分支。 |
| 生命周期 | 缓存属于项目会话或对应时间线实例；删除条目、会话切换、启动失败和插件停用时随实例释放。旧会话异步结果不得更新新会话。 |
| 验收 | 使用公开契约替换文件服务进行测试；编辑、保存、重试、离开检查和列表显示保持原有语义，性能改善由同条件基准确认。 |

项目存储继续只理解路径和不透明字节，不承担 JSON、资产、时间线或业务摘要计算。

## 第一阶段 消除重复计算

这是首批实施范围，保留现有磁盘格式、全量加载范围和公开接口。

### 只在文件内容变化时解析

修改资产、轴和事件模块，为当前文件缓存最近一次字节引用及对应解析结果。共享字节为不可变数组：相同引用可安全复用结果；引用不同则重新解析，不要求替换后的存储实现必须复用引用。

- 订阅通知与 `acceptFile` 共用解析入口，避免同一次读取被解析两次。
- 保存状态变化时，继续同步 `dirty`、`saveState`、`saveError`、`blocked` 等状态，不重新解释相同字节。
- 缓存解析失败结果；相同损坏内容不反复解析，内容变化后重新校验，保留错误及重试入口。
- 本地草稿尚未被共享存储接受时，继续以草稿为准；不能通过复用旧结果覆盖草稿。
- 文件消失或被替换时更新对应状态和缓存，保留现有删除、重建及失败处理语义。
- 新快照的公开字段均未变化时，复用旧快照并跳过通知；状态变化仍须及时发布。

完整数据的比较只在内容确实变化后执行，避免在每次无关通知中重新序列化整个资产或事件集合。

### 元数据按文件复用

`timelineListFiles` 按路径和字节引用缓存解码结果；`timelineListModel` 按条目编号和内容缓存解析、校验结果。保存状态单独更新，不触发内容重解析。

条目成员及排序字段不变时复用顺序；只变更保存状态或其他显示字段时更新对应条目。无关文件通知不重新构造整份列表，也不触发下游汇总。解码和校验错误同样参与缓存，修复文件后能够恢复。

### 只汇总变化的时间线

在时间线会话内按条目编号缓存派生摘要，记录其元数据、事件集合、轴设置及必要的加载状态。

- 某条时间线的事件或轴设置变化，只重新计算该条目的数量和时间范围。
- 选中项、保存状态或错误提示变化，不扫描其他时间线的事件。
- 元数据变化时更新对应显示字段，复用仍然有效的事件统计。
- 新建、删除或重新加载条目时更新缓存；未变化条目保持对象引用稳定。

首阶段保持现有通知时序，优先减少每次通知的工作量；通知合并或延迟发布留到确有必要时单独验证，避免改变同步读取快照和离开检查的行为。

## 第二阶段 按复测结果调整加载

第一阶段完成并通过回归后，再处理剩余瓶颈，不将这些改动作为首阶段的前置条件。

| 剩余瓶颈 | 优化方向 | 实施条件 |
| --- | --- | --- |
| 重复查询轴、事件目录 | 时间线加载批次内共用目录查询结果，并在新建、删除、显式重试时更新 | 明确查询结果有效期；目录错误不能当作空目录，不能隐藏外部文件变化 |
| 一次加载全部事件仍明显影响操作 | 优先加载当前时间线，其余按受控批次加载，让界面在批次间处理输入 | 保持最终统计准确；快速切换时优先满足最新选择，退出时取消后续调度并处理已接受操作 |
| 隐藏页面仍计算大量内容 | 根据面板激活状态推迟昂贵的筛选和派生计算，保留编辑状态 | 不通过随意卸载页面丢失草稿、选择或滚动位置 |
| 资产或时间线列表渲染成为主要耗时 | 预建资产编号索引，减少重复查找；必要时只渲染可见列表项 | 验证选择、键盘、右键菜单、滚动和不同高度内容行为 |
| 字节转换、原生文件调用仍占主要耗时 | 分别测量复制与校验、通信及原生锁等待，再优化通用文件实现 | 保留不可变字节、路径校验、冲突保护及保存顺序，不以盲目并发读取替代测量 |

**完全按需加载需要另行明确列表摘要。** 当前公开 `eventCount` 表示已加载事件数，`period` 表示已知范围，界面没有独立的摘要加载状态。直接停止加载未选中的时间线，会让列表长期显示不完整结果。实施前须确定后台补齐规则，或在 SDK 中补充明确的摘要状态，并同步更新大纲消费者。持久化摘要如确有必要，应由时间线插件拥有，明确旧项目兼容、缓存失效和重建规则。

## 数据与生命周期保护

以下行为是验收条件，不能为了减少通知而跳过：

- 共享文件的内容、保存状态和全局阻塞状态分别判断；字节相同不代表保存状态相同。
- 首次创建失败、写入未被接受和自动保存失败时，保留本地草稿、待创建及待写入状态；重试成功后才按原规则清理。
- 资产待确认编号仍仅在文件干净且保存成功后清理。
- 损坏 JSON、非法 UTF-8、读取失败及保存冲突继续显示错误，不能改写为空数据。
- 编辑中或保存失败时保留工作台离开拦截；已接受的文件操作仍由项目存储统一排空和保存。
- 项目切换、启动回滚、删除及停用时清理订阅与缓存；后台任务使用实例存活及请求代次检查，防止过期结果回写。

## 验证与性能验收

### 固定测量方式

先把上一轮临时测量方式整理成可重复运行的只读基准脚本，再测优化前后结果。脚本使用现有启动测试夹具，通过文件服务契约提供项目字节，拒绝写入；仅读取测试项目，不修改用户数据。

固定同一机器、构建方式和数据版本，记录文件数量、事件及资产数量、总字节数。各组至少运行 5 次，记录中位数及最慢值，并区分首次启动与重复打开。

模型基准记录打开操作完成和全部数据加载完成两个时间点，以及解码、解析、摘要计算、文件读取和目录查询次数。真实桌面另测点击打开到可操作、首条时间线可操作、全部数据完成的时间，并检查输入响应和内存。模型结果不能替代真实桌面结果。

### 第一阶段验收标准

| 维度 | 标准 |
| --- | --- |
| 无关通知 | 加载或保存其他文件，不增加未变化资产、轴、事件和元数据的解码、解析次数 |
| 内容版本 | 当前字节版本在订阅和读取返回两条路径间只解析一次；换入新字节时重新校验并准确更新结果 |
| 摘要计算 | 修改一条时间线的事件或轴，只重算受影响条目；其他条目引用保持稳定 |
| 状态通知 | 字节不变时，保存中、保存失败、重试成功及阻塞变化仍能及时到达消费者 |
| 加载完整性 | 固定测试项目最终加载 26 条时间线、2158 个事件及 668 个资产，范围、顺序和内容与基准一致 |
| 模型耗时目标 | 在重建的同条件基准中，打开操作中位数较优化前下降至少 70%，争取控制在 3 秒内；该数值为待验证目标 |
| 真实桌面 | 重复打开、加载期间操作及打开首条时间线的响应改善；记录剩余卡顿对应的调用栈，决定第二阶段范围 |

### 必须覆盖的回归场景

扩展现有资产、轴、事件、时间线列表、插件会话及项目存储测试，覆盖以下行为：

1. 无关通知、相同字节但保存状态变化、单文件内容变化，以及返回新字节数组的兼容文件服务。
2. 新建、修改、删除、文件重建、非法内容、读取失败及修复后重试。
3. 首次创建失败后的草稿、待写入内容、保存中继续编辑、保存冲突及失败重试。
4. 加载或保存期间切换项目、离开被拒绝、启动中途失败、插件停用，以及旧异步结果返回。
5. 资产引用选择、列表事件数和时间范围、画布编辑及原有拖拽与 400% 刻度清晰度。

运行相关测试与 `pnpm build`。真实桌面确认加载期间能够操作界面，且保存、退出和再次打开后内容一致。性能统计通过基准和测试采集，不给生产订阅路径增加长期日志负担。

## 实施顺序与交付

1. **建立可复测基准**：提交只读脚本、固定数据说明及优化前结果。
2. **完成第一阶段**：资产和轴事件缓存、元数据复用、按条目汇总及相应回归测试。
3. **复测并验收**：记录模型与真实桌面结果，确认数据、错误和保存行为一致。
4. **确定第二阶段范围**：仅针对仍占主要耗时的加载、列表或文件链路继续优化。

每批改动独立验证，便于定位回归和回退。首阶段无需数据迁移；如后续涉及 SDK 或磁盘格式变化，应在实施前补充契约、兼容和失败恢复设计。

## 第一阶段实施结果

已完成资产、轴和事件的解析缓存，元数据解码与校验复用，以及按条目缓存事件数量和时间范围。保存状态、错误和阻塞状态独立同步；公开字段不变时复用快照，不重复通知。解析前检查实例存活和请求代次，销毁时释放缓存。

实现位于原有资产和时间线插件内，继续使用现有 SDK、布局登记与共享项目字节服务。第一阶段保留全部时间线加载，不修改磁盘格式。

### 模型复测

使用同一只读脚本，前后各运行 5 个独立 Node 进程；源码编译和磁盘预读不计入计时。输入为 79 个文件、3,763,861 字节，全部样本的输入摘要、加载结果及文件操作次数一致。每次最终均得到 26 条时间线、2158 个事件、668 个资产，时间线顺序和时间范围与基线一致。

| 指标 | 优化前 | 第一阶段后 |
| --- | --- | --- |
| 打开操作完成时间中位数 | 16.789 秒 | 1.144 秒 |
| 打开操作最慢一次 | 20.641 秒 | 1.193 秒 |
| 资产文件解码次数 | 81 | 1 |
| 元数据解码次数 | 1181 | 26 |
| 轴文件解码次数 | 1054 | 26 |
| 事件文件解码次数 | 1028 | 26 |
| 摘要中的事件数值换算次数 | 3,460,292 | 2158 |
| 文件读取及目录查询次数 | 79 次读取、54 次查询 | 79 次读取、54 次查询 |

模型打开耗时中位数下降约 **93.2%**，达到第一阶段目标。该结果不包含原生桌面通信、真实文件树扫描和界面渲染。

复测脚本为 [measure-project-open.mjs](../../scripts/measure-project-open.mjs)，逐次数据、输入及实现摘要、完整加载结果和验证统计保存在[测量记录](大型项目打开性能优化测量.json)。在仓库根目录运行：

```sh
node scripts/measure-project-open.mjs --project ./测试项目 --runs 5 --output /private/tmp/lodestory-open.json
```

比较其他版本时，用 `--source-root /path/to/baseline` 指定包含源码、测试夹具及相同依赖的基线副本，并使用同一项目。脚本拒绝项目写入；`--output` 仅写测量结果。

### 功能回归

- 相关模型测试共 145 项通过，覆盖共享字节、保存失败与重试、草稿保留、项目切换、退出拦截及过期异步结果。
- 时间线浏览器回归共 7 项通过，覆盖真实拖拽、缩放、400% 刻度清晰度、事件编辑和资产关联。
- `pnpm build` 通过。完整测试共 576 项：555 项通过、16 项失败、5 项跳过。16 项失败与优化前副本的失败名称及位置完全一致，集中在正文编辑、布局、页面和字体测试；5 项因环境未安装 Playwright 跳过。
- 独立审查发现的销毁后继续解析问题已修复，复核无新增发现。

### 真实 React 界面检查

使用正式入口、真实插件装配及 ReactDOM，在 Chrome 中完成项目打开、26 条时间线加载、画布切换、事件关联资产显示、取消编辑、返回欢迎页与重新打开。控制台错误和运行异常均为 0，项目写入调用为 0。

此检查把原生命令替换为浏览器内存中的只读文件映射。点击打开到时间线列表可交互约 3.36 秒，首条画布约 3.39 秒；首次与重开分别记录约 3.32 秒、3.22 秒的连续主线程任务。这段测量覆盖内存加载及界面更新的整体过程，不能单独归为渲染耗时，也不能替代真实 Tauri、WebKit 和原生文件系统测量。

第二阶段应先在真实桌面中分段测量剩余任务，再决定是否调整加载批次、共享字节处理或列表渲染。

## 第二阶段实施结果

### 真实桌面测量范围

使用实际 Tauri 2.12.0 调试宿主、系统 WKWebView、生产前端构建和原生文件系统。前端构建由本机静态服务提供；项目打开、文件读取、目录扫描和文件树查询使用原有原生命令。配置和最近项目索引隔离到临时目录，测量程序拒绝项目文件写入。

前后各测 5 轮，每轮关闭项目后重新打开；应用启动、窗口创建和前台校准在计时之外，系统文件缓存未清空。窗口临时置顶并在各工作区显示，校验真实的可见状态、焦点及动画帧响应后开始计时，结束自动关闭。早期探针连接失败和后台窗口导致的帧等待不纳入正式结果。

测量分别记录工作台可操作、时间线列表就绪、全部时间线数据就绪，以及首条画布显示真实事件标题的时间。每轮还切换两条时间线、核对画布输入后视口、返回欢迎页并再次打开。

### 确认的瓶颈与改动

原生文件操作耗时很小：优化前 5 轮共 395 次文件读取和 270 次目录查询，实际存储闭包合计约 241 毫秒。另一份诊断构建中，`copyBytes` 的同步调用累计约 12.19 秒，校验记录和构造缓冲各执行了一遍完整复制、校验及冻结；构造和校验的计时包含 `copyBytes`，不能相加。

因此本轮改动限定在 `project-storage` 插件的通用字节处理：

- 校验原生返回记录时，保留规范化后的不可变字节，并把它交给共享缓冲安装。
- 用私有弱引用集合登记由本模块完整复制、校验并冻结的数组。再次遇到同一数组时安全复用，避免缓冲构造时再走一遍完整处理；外部数组即使已经冻结，也仍需复制和校验。
- 字节范围校验使用直接循环，保留原有类型、整数及 0 到 255 范围限制。稀疏数组、非整数和非法数值仍被拒绝。

数据和保存流程仍由原来的 `ProjectFiles`、`FileSession` 拥有；弱引用集合不持有项目内容，不新增缓冲或保存定时器，数组不再被引用后可回收。SDK、原生文件接口、磁盘格式、工作台参与者和 UI 登记方式均保持原有契约，未调整加载范围或通知时序。

## 剩余加载停顿优化结果

### 定位结果与实现边界

针对上一轮约 0.64 秒的最长前台帧间隔，单独在真实 WKWebView 中读取 1,220,058 字节的资产文件并分段计时：复制约 6 毫秒、字节校验约 6 毫秒、`Object.freeze` 约 549 毫秒。原生实际读取约 0.88 毫秒，包含通信和桥接的调用约 99 毫秒。这份单文件诊断用于确认冻结成本，不能与项目打开的帧间隔直接相加。

改动继续归属 `project-storage` 插件，复用原来的共享缓冲、工作台离开检查与保存队列：

- 原生读取和创建响应先同步捕获元数据和输入字节；64 KiB 以下保留原来的校验、冻结方式。
- 较大响应逐批校验字节并定义不可写、不可删除的普通数组索引，最后禁止扩展。结果仍是密集的普通 `Array`，长度和索引描述符与冻结数组一致，`Object.isFrozen` 为真；没有取消不可变保护或改变 SDK 字节类型。
- 每批最多 2048 个字节，每 32 项检查约 3.5 毫秒的时间预算，批次之间通过 `MessageChannel` 让界面处理输入和绘制；不可用时退回零延时定时器。该预算不是单次引擎操作或垃圾回收耗时的硬上限。
- 完整复制成功后才安装缓冲及发布快照；部分数组不对消费者可见。初始化失败会关闭调度资源，离开和停用仍等待已接受操作完成；读取期间产生的新编辑仍保留原来的冲突基线。

调度属于单次文件操作，完成或失败时关闭端口和定时器，不新增项目缓冲或保存流程。同步 `write` 和创建输入的隔离边界保持原样。SDK、原生命令、磁盘格式、插件依赖和 UI 登记方式均未变。

## 超大 TXT 打开优化

> 状态说明（2026-10）：本节记录此前的大 TXT 编辑实现及其测量结果。当前 `rich-text-editor` 未注册 `plain-text` 格式，原 CodeMirror 大文本驱动已移除；Markdown 代码块仍由 Milkdown 提供。以下实现细节和数据作为历史记录保留，不代表当前的大 TXT 编辑能力。

### 原因与归属

测试项目的完整原文为 18,776,845 字节、198,036 个换行，状态栏计数为 6,049,677 字。原应用配置把 TXT 交给 Quill，一次性 `setText` 为整篇建立段落；真实 WKWebView 隔离诊断中，全书导入直到整个诊断 45 秒超时仍未返回。这是未完成任务的观察边界，不是精确加载耗时。

本次继续扩展原有插件：

| 要求 | 实施 |
| --- | --- |
| 归属 | `rich-text-editor` 拥有大 TXT 的 CodeMirror 编辑实现；`documents` 拥有 UTF-8 解码及文本缓存；`writing-status` 拥有字数派生计算。 |
| 协作 | 沿用 `EditorProps` 完整字符串回调、`DocumentWorkspace` 和公开 `ProjectFiles`；共享字节、保存队列和冲突基线仍由项目存储拥有。没有新增 SDK 或跨插件私有依赖。 |
| 接入 | 继续使用原有正文编辑器登记和默认配置；插件内部选择驱动，应用入口、工作台布局不增加文档大小分支。 |
| 生命周期 | 每份文档独立持有视图、选区和撤销历史；隐藏时禁用编辑，关闭时销毁视图。解码属于已接受的打开操作，批次间核对来源版本；换版、删除或释放后停止旧任务并关闭调度资源。 |
| 验收 | 覆盖完整内容回声、输入法、粘贴、搜索、撤销、切换、外部替换、保存失败恢复、退出检查和重新打开；用真实桌面核对完整原文与编辑器模型的摘要。 |

### 实现

- 打开时达到 256 Ki 个 UTF-16 字符，或 5000 行的纯文本采用 CodeMirror 的可见区域渲染。全文仍在模型中，普通 TXT 和富文本继续使用原驱动。一次编辑会话内固定驱动，避免文档缩短时更换实现而丢失历史；小文档打开后再粘贴增长的性能不在本次路由优化范围内。
- 同一字节版本只解码一次，保存状态和错误变化复用内容字符串并同步更新元数据。首次打开至少 1 MiB 的新文本路径时，用 64 KiB 缓冲区分批流式解码；严格 UTF-8、BOM 和尾部换行规则保持一致，完整校验成功后才发布文本。
- 字数统计按 UTF-16 扫描并正确合并代理对，保留原有 JavaScript 空白过滤语义；按文本缓存结果，减少保存状态变化时的重复扫描及巨型字符数组分配。
- 初始化及宿主内容回声不触发编辑；外部替换清除旧历史，保留视图和搜索面板。修复了编辑器延迟创建期间收到新内容却未应用的既有问题。

### 测量与边界

使用同一个 Tauri 调试宿主及系统 WKWebView，源文件内容摘要保持一致：

| 测量范围 | 结果 |
| --- | --- |
| 内容已就绪后的编辑器初始化，3 轮 | 124、67、70 毫秒，中位数 70 毫秒 |
| 同一原文的状态栏计数 | 原诊断约 188 毫秒；新实现 40、34、37 毫秒 |
| 全书模型 / 可见行 DOM | 198,037 行 / 34 行；初始化触发编辑次数为 0 |
| 完整应用首次点击原文到可输入 | 有效前台样本 11.413 秒，其中标签出现后约 113 毫秒可输入 |
| 完整应用最长前台帧间隔 | 分批解码后样本为 902 毫秒；解码前的中间样本为 1610 毫秒 |

隔离初始化不包含原生读取、字节桥接和项目存储，不能把 70 毫秒写成整份文档的打开时间。完整打开仍主要受大字节缓冲读取及不可变规范化影响；两个整应用数据均为单次样本，不据此声称整体耗时有统计性下降。最后补充过期解码提前停止后的重测转入后台而被拒收，未覆盖已有有效样本。

编辑器模型的 UTF-8 摘要与按原有 Quill 规则归一为 LF 的完整原文一致。未编辑时原始 BOM/CRLF 字节保持原样；真实编辑后继续按编辑器完整字符串保存。本次保留同步内容上报和原有保存链路，超大文本编辑后的编码、字节复制和保存仍是全量操作，不承诺每次输入或保存都没有停顿。

输入、中文输入法、粘贴、撤销/重做、搜索定位、只读、切换、转换失败和清理均通过真实 Chrome 回归。超过 1 MiB 的 BOM/CRLF 文本通过共享存储回归，验证未编辑不写文件、编辑后保存、失败保留草稿、离开拦截、重试及重开一致。独立审查提出的过期任务继续解码问题已补充提前停止和删除场景测试。

完整数据、测量范围和原始记录见[超大文档测量](超大文档打开性能优化测量.json)。

最终构建与差异检查通过。完整回归共 623 项：603 项通过、15 项既有失败、5 项环境跳过，无新增失败；原有 16 项失败中的编辑器创建期间内容更新用例已修复。大文本真实浏览器共 9 项检查通过，文档、存储和编辑器相关模型回归通过。
