## 当前起点

[插件内核](/Users/yinzhenpu/projects/Lodestory/src/plugin-core/index.ts) 已提供能力注册与查询、依赖检查、批量装配、事件订阅与发布，以及失败和卸载清理。

但 [main.tsx](/Users/yinzhenpu/projects/Lodestory/src/main.tsx) 仍直接渲染 React；[App.tsx](/Users/yinzhenpu/projects/Lodestory/src/App.tsx) 自己启动主题同步；设置页直接调用主题实现。因此，内核尚未参与应用的真实启动和业务调用。

## 第一步 定义主题能力契约

页面现在直接依赖主题实现。要让页面使用注册的能力，先约定它需要哪些接口，再用共享标识找到实现。

已新增 [themeService.ts](/Users/yinzhenpu/projects/Lodestory/src/theme/themeService.ts)，定义：

```ts
import { createServiceKey } from "../plugin-core";
import type { ThemeMode, ThemeSnapshot } from "./themeStore";

export type ThemeService = {
  getSnapshot(): ThemeSnapshot;
  subscribe(listener: () => void): () => void;
  setMode(mode: ThemeMode): void;
  retry(): void;
};

export const themeKey = createServiceKey<ThemeService>("app/theme");
```

`ThemeSnapshot`、`ThemeMode` 沿用现有类型，并通过类型导入引用；`createServiceKey` 从插件内核导入。插件和启动入口必须导入同一个 `themeKey`，不能分别创建同名标识。

验收条件：

- [x] 契约覆盖现有读取、订阅、切换和重试行为，不向页面暴露同步启动、停止或 Tauri 对象。
- [x] 类型检查和构建通过，当前应用入口及主题调用流程未改动。

## 第二步 将主题实现包装成插件

契约只规定调用方式，主题插件负责提供实现。已新增 [themePlugin.ts](/Users/yinzhenpu/projects/Lodestory/src/theme/themePlugin.ts)，由主题插件把现有函数注册为这项能力。

使用 `createThemePlugin()` 创建插件实例，将清理函数保存在该实例的闭包中。插件 ID 固定为 `theme`，声明 `requires: []`、`provides: [themeKey]`。

`activate(context)` 按顺序执行：

1. 调用 [themeStore.ts](/Users/yinzhenpu/projects/Lodestory/src/theme/themeStore.ts) 的 `startThemeSync()`，立即保存返回的停止函数。
2. 等待 `whenNativeThemeReady()`，使原生窗口主题完成本次初始化。
3. 将 `getThemeSnapshot`、`subscribeTheme`、`setThemeMode`、`retryTheme` 映射为 `ThemeService`，通过 `context.provide(themeKey, service)` 注册。

`deactivate()` 调用并清空停止函数。即使激活只执行到一半，也能安全清理；重复执行清理不会重复释放资源。

现有原生主题调用失败会记录 `windowError`，设置保存失败会记录 `persistenceError`。继续保留这两种可重试状态，不将它们改成阻断整个应用启动的异常。插件自身激活异常仍由内核处理。

验收条件：

- [x] 单独挂载主题插件后，可以通过 `core.get(themeKey)` 取得服务并切换主题。
- [x] 激活期间能力尚不可见；激活完成后才可查询。
- [x] 卸载或激活失败后，系统外观监听、storage 监听、原生主题监听和 BroadcastChannel 均被清理，包括清理后才返回的异步监听。

验证见 [theme-plugin.test.mjs](/Users/yinzhenpu/projects/Lodestory/tests/theme-plugin.test.mjs)，覆盖初始化等待、能力调用、取消订阅、重试、重复清理、重新挂载、提交失败清理和延迟返回的监听。项目全部 77 项测试与构建通过。

这一步只新增插件，暂不改变应用启动入口。

## 第三步 新增应用启动和停止入口

主题插件可以独立运行后，需要有人创建内核并装配它。这个职责由应用入口调用的启动模块承担，不放进 React 组件。

拟新增 [createAppRuntime.ts](/Users/yinzhenpu/projects/Lodestory/src/app/createAppRuntime.ts)，提供 `startApp()`，按顺序执行：

1. 创建一个 `EngineCore`。
2. 创建本窗口的主题插件实例，调用并等待 `core.mountAll([themePlugin])`。
3. 通过 `core.get(themeKey)` 取得主题服务。
4. 返回 `{ theme, stop }`：`theme` 给页面使用，`stop(): Promise<void>` 给入口清理使用。

`stop()` 负责卸载已经启动的 `theme`，重复停止调用共享同一次清理结果。装配失败时使用内核已有回滚；若装配成功后读取服务等后续步骤失败，也要卸载已启动的插件。启动尚未完成时，入口还拿不到 `stop`，必须先等待自己持有的启动 Promise，具体顺序见第六步。

每个窗口拥有自己的内核和插件实例。现有主题模块负责跨窗口同步，不让多个窗口共享同一个 Core。

验收条件：

- [ ] `startApp()` 成功返回时，主题服务已经可用。
- [ ] 停止后，主题能力被撤销，插件监听被释放。
- [ ] 激活异常、能力未完整提供和重复停止均有可检查的结果，不留下半初始化资源。

这一步先实现并验证启动模块，仍不从 `main.tsx` 调用它。

## 第四步 切换真实启动流程

启动模块验证通过后，再一次性切换初始化的负责人，避免 App 和插件同时启动主题同步。

修改 [main.tsx](/Users/yinzhenpu/projects/Lodestory/src/main.tsx) 和 [App.tsx](/Users/yinzhenpu/projects/Lodestory/src/App.tsx)，并新增 [ThemeProvider.tsx](/Users/yinzhenpu/projects/Lodestory/src/theme/ThemeProvider.tsx)：

1. `main.tsx` 在 React 树外调用 `startApp()`，等待成功后再渲染 App。
2. `ThemeProvider` 接收启动结果中的 `theme` 对象，通过 React context 传给子组件；它只传递服务，不创建内核或启动插件。
3. `App.tsx` 删除 `startThemeSync`、`whenNativeThemeReady` 的导入、对应 effect、`themeReady` 状态和等待用的 `return null`。
4. 启动失败时，入口显示明确的启动错误；业务 App 不进入半初始化状态。

保留现有 `React.StrictMode` 和右键菜单 Provider。插件由 React 树外的入口管理，React 开发模式的组件重复挂载不会再次激活插件。主题首屏引导脚本继续负责 React 启动前的背景配色，避免初始化等待期间闪烁。

验收条件：

- [ ] 应用真实启动调用了内核的 `mountAll`，主题同步只启动一次。
- [ ] App 渲染前主题能力已经提交；初始化失败时有可见错误，不永久白屏。
- [ ] 浏览器和 Tauri 下都能正常进入页面，StrictMode 保持启用。

入口启用与 App 原初始化删除属于同一次切换，不能只完成其中一项。

## 第五步 页面改用主题能力

内核已经负责初始化，但页面此时还可能直接调用 `themeStore`。因此继续替换页面的访问入口，让实际操作也使用启动时取得的能力。

修改 [useTheme.ts](/Users/yinzhenpu/projects/Lodestory/src/theme/useTheme.ts)：从 `ThemeProvider` 取得同一个 `ThemeService`，将它的 `subscribe` 和 `getSnapshot` 交给 `useSyncExternalStore`。缺少 Provider 时明确报错，不回退到直接调用主题实现。

修改 [ThemeSettingsPage.tsx](/Users/yinzhenpu/projects/Lodestory/src/pages/ThemeSettingsPage.tsx)：读取状态继续使用 `useTheme()`；切换和重试分别调用该服务的 `setMode`、`retry`。类型可以通过类型导入引用，但页面不再运行时导入 `themeStore`。

此时真实调用链变为：

```text
main 调用 startApp
  → Core 激活主题插件
  → 主题插件启动同步并提供 themeKey 能力
  → 启动入口取得 ThemeService 并传给 ThemeProvider
  → 页面读取状态或调用 setMode
  → 主题实现更新外观和状态
  → subscribe 通知 React 读取新状态
```

验收条件：

- [ ] 设置页和主题 Hook 不再直接调用主题实现，使用的是入口取得的同一个服务对象。
- [ ] 深色、浅色、跟随系统、偏好保存、跨窗口同步和失败重试行为保持正常。
- [ ] 组件退出时取消自己的状态订阅；仅页面切换不会停用应用级主题插件。

## 第六步 接入停止和热更新清理

启动归入口管理后，React 的组件卸载只负责清理组件订阅，不能再承担主题插件的停止。因此由入口持有并调用运行实例的 `stop()`。

开发热更新按以下顺序协调：

1. 将旧入口标记为失效，阻止尚未完成的启动结果继续渲染页面。
2. 等待入口持有的旧启动 Promise 结束。内核在 `mountAll` 期间拒绝并发卸载，不能直接抢先调用 `unmount`；若启动失败，先确认内核回滚已经结束。
3. 若启动成功，卸载已渲染的旧 React 树，使组件取消订阅，再等待旧运行实例的 `stop()`。即使启动刚成功、尚未渲染就被判为失效，也要停止这个实例。
4. 旧实例清理结束后，再启动新实例；清理失败时显示错误或采用完整重载，不继续叠加监听。

在入口的 `import.meta.hot.dispose` 中触发停止，并将清理 Promise 交给下一次启动显式等待。启动失败时也要结束这条等待链，不能因旧 Promise 拒绝而跳过后续清理。

窗口退出与文档保存有先后关系：现有文档关闭保存仍由 [useDocumentWorkspace.ts](/Users/yinzhenpu/projects/Lodestory/src/documents/useDocumentWorkspace.ts) 处理。不要在关闭请求刚发生时就并行卸载内核，否则保存失败、窗口保留时，应用可能已经失去服务。后续迁移文档能力时，再统一保存完成和应用停止的顺序。

验收条件：

- [ ] 初始化尚未完成时触发热更新，也不会出现并发卸载、旧页面迟到渲染或两套主题监听。
- [ ] 清理后的原生监听即使延迟返回，也会立即解除；旧 BroadcastChannel 已关闭。
- [ ] 重复停止不会重复释放；现有文档保存失败时保留窗口和草稿的规则不受影响。
