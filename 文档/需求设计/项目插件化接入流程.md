## 第一步 定义主题能力契约

页面现在直接依赖主题实现。要让页面使用注册的能力，先约定它需要哪些接口，再用共享标识找到实现。

主题能力契约现由 SDK 的 [theme.ts](/Users/yinzhenpu/projects/Lodestory/packages/sdk/src/theme.ts) 提供，导出 `themeKey`、`ThemeService`、`ThemeMode` 和 `ThemeSnapshot`。插件和启动入口必须导入同一个 `themeKey`，不能分别创建同名标识。使用方式如下：

```ts
import type { PluginContext } from "@lodestory/sdk";
import { themeKey } from "@lodestory/sdk/theme";
import type { ThemeService, ThemeSnapshot } from "@lodestory/sdk/theme";

function readTheme(context: PluginContext): ThemeSnapshot {
  const theme: ThemeService = context.get(themeKey);
  return theme.getSnapshot();
}
```

`PluginContext`、`ThemeSnapshot`、`ThemeMode` 和 `themeKey` 使用 SDK 的公开契约；消费主题能力的插件应在 `requires` 中声明 `themeKey`，再从 `context` 读取服务。插件不得复制或重新创建同名标识。

- [x] 契约覆盖现有读取、订阅、切换和重试行为，不向页面暴露同步启动、停止或 Tauri 对象。
- [x] 类型检查和构建通过，当前应用入口及主题调用流程未改动。

## 第二步 将主题实现包装成插件

契约只规定调用方式，主题插件负责提供实现。已新增 [themePlugin.ts](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/themePlugin.ts)，由主题插件把现有函数注册为这项能力。

使用 `createThemePlugin()` 创建插件实例，将清理函数保存在该实例的闭包中。插件 ID 固定为 `theme`，声明 `requires: []`、`provides: [themeKey]`。

`activate(context)` 按顺序执行：

1. 调用 [themeStore.ts](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/themeStore.ts) 的 `startThemeSync()`，立即保存返回的停止函数。
2. 等待 `whenNativeThemeReady()`，使原生窗口主题完成本次初始化。
3. 将 `getThemeSnapshot`、`subscribeTheme`、`setThemeMode`、`retryTheme` 映射为 `ThemeService`，通过 `context.provide(themeKey, service)` 注册。

`deactivate()` 调用并清空停止函数。即使激活只执行到一半，也能安全清理；重复执行清理不会重复释放资源。

现有原生主题调用失败会记录 `windowError`，设置保存失败会记录 `persistenceError`。继续保留这两种可重试状态，不将它们改成阻断整个应用启动的异常。插件自身激活异常仍由内核处理。

验收条件：

- [x] 单独挂载主题插件后，可以通过 `core.get(themeKey)` 取得服务并切换主题。
- [x] 激活期间能力尚不可见；激活完成后才可查询。
- [x] 卸载或激活失败后，系统外观监听、storage 监听、原生主题监听和 BroadcastChannel 均被清理，包括清理后才返回的异步监听。

验证见 [theme-plugin.test.mjs](/Users/yinzhenpu/projects/Lodestory/tests/theme-plugin.test.mjs)，覆盖初始化等待、能力调用、取消订阅、重试、重复清理、重新挂载、提交失败清理和延迟返回的监听。项目测试与构建通过。

这一步只新增插件，暂不改变应用启动入口。

## 第三步 新增通用运行模块

如果运行模块自己创建主题插件并查询 `themeKey`，每增加一种业务能力就得修改运行模块；这样内核虽通用，启动运行层却仍被业务固定。因此由调用方选择插件和要取的能力，运行模块只负责创建内核、装配插件、提供能力查询和停止。

已实现的 [createAppRuntime.ts](/Users/yinzhenpu/projects/Lodestory/src/app/createAppRuntime.ts) 只依赖 `plugin-core`，导出：

```ts
export type AppRuntime = {
  get<T>(key: ServiceKey<T>): T;
  stop(): Promise<void>;
};

export function createAppRuntime(
  plugins: readonly Plugin[],
): Promise<AppRuntime>;
```

调用时，运行模块创建 `EngineCore` 并等待 `core.mountAll(plugins)`；装配成功后返回的 `get(key)` 委托给 `core.get(key)`，`stop()` 委托给 `core.unmountAll()`。运行模块不创建具体插件、不查询具体业务 key，`AppRuntime` 也不暴露主题字段。

`mountAll` 会按依赖决定实际激活顺序，所以 Core 记录成功激活的顺序；`unmountAll()` 按这个顺序逆序停用，不能按调用方传入数组简单倒序。某个插件清理失败时，Core 仍继续清理其余插件，最后通过 `PluginBatchDeactivationError.cleanupErrors` 保留各插件的 `pluginId` 和原始 `error`。运行模块的 `stop()` 先缓存清理 Promise，再开始执行清理；成功、失败或停用回调中的重复调用都复用同一个结果。

若 `mountAll()` 激活失败，Core 负责回滚，运行模块原样抛出包含激活与回滚结果的错误。应用拿到运行实例后，若取具体能力或渲染失败，则由应用入口持有该实例、调用 `stop()`，并同时保留原错误和清理错误。

每个窗口创建自己的运行实例。运行模块不负责跨窗口同步，具体插件沿用各自已有的同步方式。

验收条件：

- [x] 运行模块只依赖插件内核；传入任意插件列表后，等待装配完成并返回通用 `get`、`stop`。
- [x] 假插件验证能力查询、激活失败回滚、按实际激活顺序逆序清理，以及一个清理失败后继续清理其余插件。
- [x] `stop()` 的重复调用复用同一个成功或失败 Promise；测试不导入主题实现。

验证见 [app-runtime.test.mjs](/Users/yinzhenpu/projects/Lodestory/tests/app-runtime.test.mjs) 和 [plugin-core.test.mjs](/Users/yinzhenpu/projects/Lodestory/tests/plugin-core.test.mjs)：使用通用假插件验证运行、能力类型推断和清理；运行测试仅允许加载 `app`、`plugin-core` 模块，意外导入业务模块会直接报错。

第三步负责实现和验证通用运行模块；第四步再将它接入 `main.tsx`。

## 第四步 切换真实启动流程

通用运行模块验证通过后，再切换初始化的负责人，避免 App 和插件同时启动主题同步。应用入口负责业务装配，因此在这里选择主题插件并查询主题能力：

```ts
const runtime = await createAppRuntime([createThemePlugin()]);
const theme = runtime.get(themeKey);
// 将 theme 传给 ThemeProvider，再渲染应用。
```

这里显式依赖主题是应用组合业务的职责；`createAppRuntime` 仍只处理插件列表和能力 key。

已修改 [main.tsx](/Users/yinzhenpu/projects/Lodestory/src/main.tsx) 和 [App.tsx](/Users/yinzhenpu/projects/Lodestory/src/App.tsx)，并新增 [ThemeProvider.tsx](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/ThemeProvider.tsx)：

1. `main.tsx` 在 React 树外调用 `createAppRuntime([createThemePlugin()])`，等待成功后用 `runtime.get(themeKey)` 取得服务，再将 `theme` 传给 `ThemeProvider`。
2. `ThemeProvider` 通过 React context 把传入的服务交给子组件；它只传递服务，不创建内核或启动插件。
3. `App.tsx` 删除 `startThemeSync`、`whenNativeThemeReady` 的导入、对应 effect、`themeReady` 状态和等待用的 `return null`。
4. `createAppRuntime` 装配失败时 Core 已回滚，入口显示明确的启动错误；业务 App 不进入半初始化状态。
5. runtime 返回后，若 `get(themeKey)`、React 根节点创建或渲染失败，入口先卸载 React 树，再调用 `stop()`。React 异步渲染错误由 `createRoot` 的 `onUncaughtError` 交给同一个错误处理函数；清理排入微任务，重复错误只清理一次。错误页面直接用 DOM 显示“应用启动失败”和重新加载按钮；原始错误与所有清理错误同时保留在控制台。

保留现有 `React.StrictMode` 和右键菜单 Provider。插件由 React 树外的入口管理，React 开发模式的组件重复挂载不会再次激活插件。主题首屏引导脚本继续负责 React 启动前的背景配色，避免初始化等待期间闪烁。

- [x] App 渲染前主题能力已经提交；初始化失败时有可见错误，不永久白屏。
- [x] 浏览器可正常进入欢迎页及设置页，控制台没有警告或错误，StrictMode 保持启用。
- [ ] Tauri 实机启动检查；原生初始化等待、可恢复错误及失败清理由模拟接口测试验证。

入口测试见 [app-startup.test.mjs](/Users/yinzhenpu/projects/Lodestory/tests/app-startup.test.mjs)，项目测试与构建通过。页面 Hook 与设置页的访问替换、正常退出和热更新清理仍分别属于第五步、第六步。

## 第五步 页面改用主题能力

应用入口已从通用 runtime 取得 `ThemeService`，但页面此时还可能直接调用 `themeStore`。因此继续替换页面的访问入口，让实际操作也使用入口传下来的同一个能力。

修改 [useTheme.ts](/Users/yinzhenpu/projects/Lodestory/src/plugins/theme/useTheme.ts)：从 `ThemeProvider` 取得同一个 `ThemeService`，将它的 `subscribe` 和 `getSnapshot` 交给 `useSyncExternalStore`。缺少 Provider 时明确报错，不回退到直接调用主题实现。

修改 [ThemeSettingsPage.tsx](/Users/yinzhenpu/projects/Lodestory/src/plugins/settings/ThemeSettingsPage.tsx)：读取状态继续使用 `useTheme()`；切换和重试分别调用该服务的 `setMode`、`retry`。类型可以通过类型导入引用，但页面不再运行时导入 `themeStore`。

此时真实调用链变为：

```text
main 选择 createThemePlugin 并调用 createAppRuntime
  → Core 激活主题插件
  → 主题插件启动同步并提供 themeKey 能力
  → 应用入口通过 runtime.get(themeKey) 取得 ThemeService 并传给 ThemeProvider
  → 页面读取状态或调用 setMode
  → 主题实现更新外观和状态
  → subscribe 通知 React 读取新状态
```

验收条件：

- [ ] 设置页和主题 Hook 不再直接调用主题实现，使用的是入口取得的同一个服务对象。
- [ ] 深色、浅色、跟随系统、偏好保存、跨窗口同步和失败重试行为保持正常。
- [ ] 组件退出时取消自己的状态订阅；仅页面切换不会停用应用级主题插件。

## 第六步 接入停止和热更新清理

运行实例由入口持有后，React 的组件卸载只负责清理组件订阅，不能再承担插件停止。因此由入口持有并调用运行实例的 `stop()`；运行模块再通过 `core.unmountAll()` 停用所有已激活插件。

开发热更新按以下顺序协调：

1. 将旧入口标记为失效，阻止尚未完成的启动结果继续渲染页面。
2. 等待入口持有的旧启动 Promise 结束。内核在 `mountAll` 期间拒绝并发卸载，不能直接抢先清理；若启动失败，先确认 Core 回滚已经结束。
3. 若启动成功，入口保存 runtime；卸载已渲染的旧 React 树，使组件取消订阅，再等待旧 runtime 的 `stop()`。即使启动刚成功、尚未渲染就被判为失效，也要停止这个实例。
4. 旧实例清理结束后，再启动新实例；清理失败时显示错误或采用完整重载，不继续叠加监听。

在入口的 `import.meta.hot.dispose` 中触发停止，并将清理 Promise 交给下一次启动显式等待。`stop()` 通过 `unmountAll()` 按实际激活顺序逆序清理；即使个别插件清理失败，Core 也要尝试其余插件，并以 `PluginBatchDeactivationError.cleanupErrors` 汇总失败。启动失败时由 `mountAll()` 完成回滚，也要结束这条等待链，不能因旧 Promise 拒绝而跳过后续启动。

若 runtime 已返回，但应用入口取能力或渲染失败，错误处理路径仍持有 runtime 并调用 `stop()`；原始业务错误和 `stop()` 的清理错误都要留给用户和日志查看。

窗口退出与文档保存有先后关系：现有文档关闭保存仍由 [useDocumentWorkspace.ts](/Users/yinzhenpu/projects/Lodestory/src/documents/useDocumentWorkspace.ts) 处理。不要在关闭请求刚发生时就并行卸载内核，否则保存失败、窗口保留时，应用可能已经失去服务。后续迁移文档能力时，再统一保存完成和应用停止的顺序。

验收条件：

- [ ] 初始化尚未完成时触发热更新，也不会出现并发卸载、旧页面迟到渲染或两套主题监听；能力读取或渲染失败会停止 runtime 并保留原错与清理错。
- [ ] 清理后的原生监听即使延迟返回，也会立即解除；旧 BroadcastChannel 已关闭。
- [ ] 重复停止不会重复释放；现有文档保存失败时保留窗口和草稿的规则不受影响。
